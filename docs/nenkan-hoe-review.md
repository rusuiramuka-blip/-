対象：`年間法会受付管理｜春彼岸・お盆・秋彼岸`（`14WpiSyv…`）に紐づく拡張スクリプト。
実シート（設定／受付入力／申込管理／作札一覧／読経対象一覧／納骨壇名簿／一般信者名簿／
初盆電話受付／入金履歴／申込履歴索引／未納確認）の構成・実データと突き合わせて確認した。

## 1. 不具合（動作が誤っていたもの）

### 1-1. 初盆電話受付の入金一括同期が一度も効いていない　★要修正
`syncFirstObonPaymentsBatch_` が **B列（受付日時）** を申込IDとして照合していた。
初盆電話受付の申込IDは **V列（備考）の「申込ID：〜」** にしかないため、
`stateMap.get()` が常に空振りし、入金状況・入金方法・入金日が更新されないまま
「現在値をそのまま書き戻す」だけになっていた（エラーも出ないので気付きにくい）。

- 影響：`syncAllPaymentSummaries_` / `syncAllOperationalStatuses_`（初期設定・入金再計算）で
  初盆シートの入金欄が更新されない。1件ずつの `syncFirstObonPaymentFromApplication_` は正常だったため、
  「申込管理を直接編集したときは直るが、再集計では直らない」状態だった。
- 修正：`firstObonRowsByApplicationId_()` を追加し、V列の「申込ID：〜」から行を引く。

### 1-2. 一般・初盆の受付が、クレジット／コンビニを選ぶと必ず「要確認」になる　★要修正
`registerManualReception_` は
`isOnlinePayment_(paymentRaw) && paymentPlan.items.some(item => !item.url)` で
「オンライン決済の商品URLが未設定」を付けていたが、

- `productUrl_()` は区分「一般」で必ず空文字を返す（v21で一般お盆フォームとURL設定を廃止済み）
- 初盆は `buildPaymentPlan_` が該当分岐を持たず、**納骨壇/一般の合同供養単価**で明細を作っていた
  （合計額は正しいが明細は誤り。20,000円が「5,000円×1」等になる）

ため、一般・初盆でオンライン決済を選ぶと**構造上必ず要確認**になっていた。

- 修正：`requiresEcProductUrl_()` を追加し、EC商品を持つ「納骨壇の通常申込」だけを判定対象に。
  `buildPaymentPlan_` に初盆分岐（1件・志納料そのまま・URLなし）を追加。
  申込管理の訂正時にも同じ判定を通し、既存行の古い「商品URL未設定」は訂正で消えるようにした。

### 1-3. 名簿の直近3年同期が O(名簿件数 × 台帳件数)　★要修正（実行時間上限）
`syncRecentHistoryToMasters_` が名簿1行ごとに `compactRecentHistoryText_()` を呼び、
その中で毎回 `申込管理` 全体と `申込履歴索引` 全体を読み直していた。
さらに `restoreNokotsuObonHistoryFormulas_` は1行につき `setFormula` を3回実行していた。

- 影響：納骨壇名簿・一般信者名簿が数百行規模になると、`runV22Setup` /
  「直近3年の申込履歴を同期」が6分の実行時間上限に達する危険がある。
- 修正：直近3年の照合表を実行中1回だけ作って共有（`getRecentHistoryData_`）。
  名簿への書き戻しも列単位の `setValues` / `setFormulas` に集約。

### 1-4. 受付入力で「今回入金額」を先に入力すると消える
入金状況が「未入金」のまま金額（B23）を入れると、次の編集で
`updateManualV16Preview_` が金額を消していた（入金状況を先に選ぶ前提のコード）。

- 修正：金額を入力した時点で志納料（D22）と比較し、
  `入金済`／`一部入金` を自動選択したうえで入金日も補完するようにした。

### 1-5. 志納料表の参照が固定範囲（A5:E8）
`getFeeRule_` が `設定!A5:E8` 固定。現在の設定シートは
5行目=春彼岸/納骨壇 … 9行目=お盆/初盆 なので、**設定シートに1行足すと金額判定が静かにずれる**。

- 修正：法会名＋対象区分の名称照合に変更（`getFeeRows_`）。初盆料金の取得も同じ表から行う。
- あわせて「設定状態を確認」に志納料表（4区分＋初盆）の点検を追加。

## 3. スクリプトでは直さず、運用として決めていただきたい点

### 3-1. 「〇〇家先祖」と「〇〇家先祖代々」の表記ゆれ　★要判断
- 設定シートの運用ルール：**「先祖は〇〇家先祖」**
- スクリプト（v22の `normalizeAncestorMemorialName_`）：**「〇〇家先祖代々」** へ正規化
- 実データ：作札一覧には旧版で作られた `深町家先祖` `大石家先祖` が残っている

このままだと、同じ方でも訂正した行だけ「先祖代々」になる。
どちらかに統一が必要（コードは現状「先祖代々」のまま。設定シート文言を合わせるか、
コード側を「〇〇家先祖」に戻すかをご指示ください）。

### 3-2. 申込管理で電話番号（J列）を非表示にしている
`simplifyAnnualWorkbookV20_` がI:J（施主フリガナ・電話）を隠している。
連絡先はらくまる寺務で管理という方針だが、未納の督促時に台帳から電話が見えないのは
不便な場面がありそう。表示に戻すかはご判断ください。

### 3-3. フォーム送信時のスキーマ検査は「全部止める」設計
`onAnnualMemorialFormSubmit` は先頭で `assertAnnualV17SchemaReady_` を呼び、
1つでも列構成が崩れていると送信を例外で止める（内容は「受信エラー」シートに記録され、
フォーム所有者にエラーメールが届く）。
台帳の整合性は守られるが、**申込者には自動返信が届かない**ので、
受信エラーシートは定期的に確認する運用が要る（現状は0件）。

### 3-4. 参考：現在の実データで確認した挙動
- 秋彼岸2026の8件は、志納料（3,000／2,000／4,000／6,000円）・未収額・
  読経対象（納骨壇名簿の同壇者を全員展開）とも計算どおり。
- 未納確認の集計（未入金7件・未収22,000円）も一致。
- お盆・納骨壇フォームには「初盆受付の確認」設問があり、
  `validateApplication_` の初盆チェックは成立する（秋彼岸フォームには不要なので問題なし）。

1. Apps Scriptエディタで既存コードを全選択し、
   `apps-script/nenkan-hoe/年間法会受付.gs` の内容で置き換えて保存。
2. スプレッドシートを開き直す（メニューが3項目＋管理サブメニューになる）。
3. 「通年法会受付 > 管理（初期設定・同期）> 計算ロジックの自己診断」を実行し、
   「すべて正常です」を確認。
4. 「管理（初期設定・同期）> 初期設定を実行（v22）」を1回実行。
   （列構成・トリガー・履歴索引・入金集計・使い方シートを更新。外部ファイルも読むので
   フォーム所有者アカウントで実行し、初回は権限承認が要る）
5. 「設定状態を確認」で、フォーム連携・トリガー・志納料表・初盆電話受付まで
   正常表示になることを確認。
6. 既存の一般・初盆の申込に「オンライン決済の商品URLが未設定」が残っている場合は、
   申込管理でAA列「修正反映」をチェックすると再判定されて消える。

## 1. 寺院一任の確定日時が重複チェックを通らない　★最重要

v22.3 で寺院一任にも確定日時を持たせられるようになりましたが、

## 2. 受付入力のプレビューが「ご希望の供養未選択」を警告しない

現在の受付入力（阿部一久様・秋彼岸・納骨壇）は

登録を押すと `ご希望の供養を選択してください` で弾かれますが、押すまで分かりません。
読経参列の未選択・寺院一任の日時片側入力も同様にプレビュー対象外です。

`'読経対象一覧'!R2:R="受付中"` のため、受付状態が「保留」の申込は当日一覧に出ません。
未納確認は保留も集計する方針なので、当日の読み上げだけ漏れる形になります。

読経対象一覧が空のとき FILTER が #N/A になり、B2 の年度プルダウンが壊れます。

0. の状態（AA=TRUE／AB空）は画面上ほぼ見分けが付きません。
「設定状態を確認」で未反映行を件数表示すると、同じ取りこぼしを防げます。

## 6. 確認しておきたい点（環境依存）

- 読経対象一覧 U:W（読経申込者名・フリガナ）が**行ごとの数式**の場合、
  `writeFirstEmptyIdRow_` は書式と入力規則しかコピーしないため、

  読経対象一覧を裏方化した現行運用と合いません（非表示行なので実害はありません）。

## C. 「同じ読経日時に先約があります」が修正反映で消えない

`validateReadingSlotConflict_` は v22.6 で文言を
「同じ読経希望日時に先約があります」→「**同じ読経日時に先約があります**」へ変更したが、
`isCorrectionRecheckIssue_` の再判定リストは旧文言のままなので、
一度付いた要確認理由が `preservedIssues` として永久に残る。

## D. 受付状態（AD列）変更後、読経用一覧のチェックがずれる

`syncOperationalStatus_` は読経対象一覧 R列（受付状態）を書き換える。R列は読経用一覧の

ところが `onAnnualMemorialEdit` の AD列分岐は `syncReadingViewCheckboxes_` を呼ばないため、
A列のチェックだけが旧位置に残り、別の申込が読経済に見える。

## E. 申込履歴索引の全件再構築が既存行を消していない

`syncRecentApplicationHistory_` は `indexSh.getRange(2,1,rows.length,9).setValues(...)` で
上書きするだけなので、受付ごとに追記された既存行が `rows.length` を超えていると末尾に残る。
A の入口を戻すと表面化するため、同時に修正する。

## 適用した修正（v22.7）

1. 保守用の公開入口 `runAnnualMemorialSetup` / `importRecentApplicationHistory` /
   `importMemorialHistoryMasters` を追加（メニューには出さない）。
2. `oldReading` を `displayDate_` / `displayTime_` で整形してから比較。
3. `isCorrectionRecheckIssue_` に新文言を追加。
4. `onAnnualMemorialEdit` の AD列分岐後に `syncReadingViewCheckboxes_` を1回だけ実行。
5. 索引の全件再構築前に既存行をクリア。

## 残った2点

### R1. 対象範囲の判定が「受付対象年」に固定されている

`syncRecentApplicationHistory_` は一般の COVERAGE を `currentYear` で書き、
`checkAnnualMemorialSetup` は `${baseYear}|お盆|一般` を必須にしています。
`currentYear` は受付中フォームの年度・申込管理の最大年で引き上がるため、
**翌年度（2027）の春彼岸フォームを受付中にした時点で両者がずれ**、
一般信者名簿に翌年度の記録がまだない以上、設定状態を確認が恒久的に「要確認」になります。

対応：一般の COVERAGE は名簿が持つ最新年で書き、設定確認は受付対象年の印を要求せず、
一般の対象範囲が「いずれかの年で」存在するかだけを見ます。
受付対象年そのものは `renderRecentApplicationHistory_` が
`year === currentYear` で「申込なし」と確定するため、印は不要です。

### R2. 再構築の保護条件に年が直書きされている

`'2026|お盆|納骨壇'` `'2025|お盆|納骨壇'` を必須にしているため、
外部資料の権限や保管場所が変わると再取込が恒久的に失敗します。
「既に確認済みの対象範囲を失わないこと」を条件にすれば、年の保守が不要になり、
一時的に読めなかった回の巻き戻りも同じように防げます。

### R3（付随）フォーム送信トリガーに復旧手段がない

`ANNUAL.HANDLER` のトリガーを作る処理はコード上に存在せず（v22.5 で
`repairAnnualFormConnections` が削除済み）、フォーム側に紐づくトリガーは
Apps Script のトリガー画面からも作り直せません。3つのうち1つでも失われると、
設定状態を確認が `送信トリガー=2/3` と出したまま復旧できません。
管理者用の `repairAnnualFormTriggers` を1つだけ追加しました。

## 適用（v22.8）

1. 一般の対象範囲を、受付対象年固定から名簿の最新年基準へ。
2. 設定確認の期待値から受付対象年の依存を除去。
3. 再構築の保護条件を「既存の対象範囲を失わないこと」へ。
4. `repairAnnualFormTriggers` を追加（メニューには出しません）。

なお `setupAnnualMemorialV23_` と `syncMemorialHistoryMasters_` を非公開のまま残す判断は、
初回移行と構成変更が済んでいる現状では妥当です。編集・変更トリガーは
Apps Script のトリガー画面から手動で作り直せます
（実行する関数＝`onAnnualMemorialEdit` / `onAnnualMemorialChange`、
イベントのソース＝スプレッドシートから、種類＝編集時／変更時）。

# v22.10（再検証版）の確認（2026-09-04）

構文チェック（7,204行）と、索引再構築ロジックのシミュレーションで再検証しました。

## 確認できた点

- R1（年ずれ）は解消。`checkAnnualMemorialSetup` は年ではなく
  「お盆・納骨壇」「お盆・一般」の業務範囲で判定するようになり、
  当方案に残っていた `'2026|お盆|納骨壇'` `'2025|お盆|納骨壇'` の直書きも消えています。
  翌年度フォームを受付中にしても恒久的な「要確認」になりません。
- R2 は当方案（旧COVERAGEを再生成できなければ中止）より良い方式へ変更されています。
  中止せずに、確認済み年度の COVERAGE と DATA を旧索引から引き継ぐため、
  年度更新でも外部資料の一時的な不通でも取込が止まりません。3ケースで挙動を確認：

  | 状況 | COVERAGE保持 | DATA保持 | 結果 |
  |---|---|---|---|
  | 一般の最新年が2027へ進む | 1 | 1 | 2026一般の実績を保持したまま2027を追加 |
  | 2026納骨壇の資料が読めない | 1 | 1 | 2026納骨壇の実績を保持 |
  | 通常再実行 | 0 | 0 | 余分な引き継ぎなし |

- v22.9 で入った以下も妥当です。
  - `isAnnualFormSubmitTrigger_` によるイベント種類の確認（種類違いを正常扱いしない）
  - 重複トリガーを `duplicateTriggerCount` として個別に数える
  - `repairAnnualFormTriggers` の「全フォームを開く→不足分を作成→最後に削除→再検証」順序。
    途中で権限・上限エラーが起きても既存の正常トリガーが残ります。
  - インストール型トリガーが作成者ごとである点を「使い方」と診断文へ明記。
- 一般信者名簿由来の履歴IDへ対象年を含める修正（`GENERAL-MASTER-{year}-{行}`）は、
  引き継ぎ時の新旧照合（`dataReplacementKey` の MASTER 分岐）と整合しています。
- 「使い方」シートは52行・見出し行8か所とも整合。旧変数の残骸もありません。

## 残る点（対応は任意）

COVERAGE を持たない範囲の DATA は、その資料が読めなかった回に引き継がれません。
該当するのは「2025秋彼岸・納骨壇」だけです（部分資料のため COVERAGE を付けない設計）。
この資料が読めなくなると、秋彼岸の2025年表示が「● 申込あり」から
「？ 履歴未取込」へ戻ります。誤った内容にはならず、表示が控えめになるだけです。

直すなら、参照元（G列）単位で「今回1件も生成できなかった参照元」の旧行を引き継ぐ方法が
安全です。ただし「現行申込管理」だけは、申込を全件取り消した場合に旧行が復活しないよう
除外する必要があります。静的な過去資料なので、現状のままでも実害はありません。
