巫女勤怠・給与スクリプト
実シート突合レビュー

貼っていただいた 2 本のスクリプトを、実際の 2 ファイル（管理者用・現場用）の列構成・数式・実データと 1 列ずつ突き合わせて検証しました。設計の骨格は妥当ですが、シート定義との対応に致命的なズレが 3 か所あり、現状では給与を 1 件も確定できません。

管理者用 巫女勤怠・給与管理（再構築版・完成） — 11 シート 現場用 巫女シフト・現場運営（再構築版・完成） — 11 シート

総評

結論：現在のコードのままでは、承認も締めも支給も 1 件も通りません。個別のバグではなく、現場→管理の連携パイプラインが 4 箇所で切れています。逆に言えば、下記 A-1〜A-4 を直せば全体が動き出す状態です。

  1. 01

    現場から送信すると 01_勤怠承認!C（スタッフID） に「本堂1｜早番 9:00～15:00」というシフト名が入る（A-1）

  2. 02

    スタッフIDが一致しないので R 確定基本時給 の INDEX/MATCH が空になり、承認時に「時給が未設定です」で必ず停止

  3. 03

    仮に時給が入っても AL 実績連携 が「未送信」のまま。これを「実績送信済」にする処理がどちらのスクリプトにも存在しない（A-2）

  4. 04

    承認が 0 件なので 02_個人別給与 の COUNTIFS/SUMIFS は全員 0 円。締め条件（承認済件数>0）を満たす人が出ない

設計として良くできている点

  • 承認時に時給・交通費を静的値へ固定する設計。07_スタッフ・賃金 を後日改定しても過去の承認済み給与が動かない。締め時に T〜AB を凍結するのも同じ思想で一貫しています。実務でいちばん事故が起きる箇所を正しく押さえています。
  • 状態機械と解除の作法。未確認→承認済→締め済→支給済→受領済 の一方向遷移、解除には理由入力を必須にして _履歴 へ残す。監査に耐える骨格になっています。
  • 部分適用を避ける意識。approveSelectedAttendance が「全行検証 → 全行書込」の順になっている、空き行不足を書込み前に検出する、締め済み行への上書きを現場側から拒否する — いずれも正しい判断です。
  • 深夜時間の計算式。日跨ぎ勤務を「当日22時〜翌5時」と「当日0時〜5時」の 2 区間の重なりで取る式は正しく、23:00→翌06:00 で 6.0h を返します。除算前に分へ丸めているのも良い。
  • 法令値に適用開始日と出典URLを持たせている。最低賃金・割増率を年度更新する前提の作りは、この種のシートでは珍しく現実的です。

弱点の要約

コードがシートの実物ではなく「こうなっているはず」という前提で書かれており、列番号が実シートと一致していません（A-1・A-3）。またパイプラインの片側（当日実績の送信）が丸ごと未実装です（A-2）。加えて「行番号ベースの勤務ID」と「固定 500 行」という 2 つの前提が、正月編成の実データ量で破綻します（A-4・B-1）。

A-4

勤務IDが行番号依存で、2 ファイルの採番規則も食い違っている

致命
事実

02_シフト入力!A は "WK-"&TEXT($B,"yyyymmdd")&"-S"&TEXT(ROW()-4,"000")、つまり 行番号 でIDを作ります（実データ：WK-20261229-S001）。一方 01_勤怠承認 と 02A_当日勤怠 の実データは スタッフID基準の WK-20261231-M004-001。同じ「勤務ID」という名前で 2 つの体系が並走しています。

影響

送信済み行のIDは静的値に固定されますが、未送信行は行番号から再計算されます。行を 1 行削除するだけで、固定済みIDと数式IDが衝突します。assertUniqueWorkIds_ が検出して全体を止めるため、正月の繁忙期に「原因不明で送信できない」状態になります。並べ替え・フィルタ後の行挿入も同様です。

修正

IDは数式で作らず、送信時にスクリプトが採番して静的値で確定させてください。既存データに合わせるなら WK-{yyyymmdd}-{スタッフID}-{その人その日の連番}。未送信行のA列は数式ではなく空欄か「未採番」表示にし、repairShiftFormulasOnSheet_ がA列を書き戻す処理は削除します。これで A-4 と assertUniqueWorkIds_ の恒常的な誤検知が同時に消えます。

B. 重要 — 運用が止まる / データが壊れる

B-1

500 行の上限に正月編成が収まらない

重要
事実

02_シフト入力 は 5〜504 行の 500 行。現状 12/29〜1/1 の 4 日間だけで担当者入力済 138 行、最終行は 142 行目です。_設定 の対象期間は 12/29〜1/31（34 日間）。同じ密度なら 1,000 行を超えます。01_勤怠承認 も 5〜503 行で同じ天井です。

影響

nextBlankRow_ が「空き行がありません」で throw し、送信も承認も不能に。しかも満杯になるのは元日直前です。

修正

行数を実運用量（2,000 行程度）まで拡張し、FIELD.LAST_ROW / PAY_ROW.* を sheet.getMaxRows() から動的に求める形へ。数式の参照範囲（$B$5:$B$504 等）も同時に伸ばす必要があります。中期的には年度・期別にファイルを分け、_履歴 と併せてアーカイブする運用を。

B-2

onEdit が重すぎて簡易トリガの 30 秒制限に当たる

重要
事実

現場側 onEdit は編集行ごとに repairShiftFormulasOnSheet_（10 列 × setFormulas ＋ ID列の読み書き）を呼び、さらに 1 セルずつ getDisplayValue() しています。管理者側も 1 行あたり 38 列読取＋最大 6 回の書込＋appendHistory_（_履歴 の全行スキャン）です。

影響

数十行を貼り付けると数百〜数千回の API 呼び出しになり、簡易トリガの 30 秒上限を超えます。途中で落ちるため、一部の行だけ数式が復元され、一部は生値のままという最悪の中途半端な状態が残ります。

修正

①編集範囲が自動列に掛かったときだけ数式復元を走らせる（現状は 21 列すべてで発動）②行ループ内の getRange を範囲一括の getValues/setValues に置換 ③appendHistory_ は getLastRow()+1 か appendRow で末尾追記し、複数行分は 1 回の setValues にまとめる。

B-3

例外が書込ループの途中で投げられ、部分適用が残る

重要
事実

sendConfirmedShifts の書込ループ内に締め済チェックの throw が残っています（事前チェック済みでも、他の人が同時に締めれば発生します）。Apps Script にロールバックはないため、前半の行だけ管理者側へ同期された状態で止まります。

あわせて

releaseSelectedClose は 1 件ごとに 01_勤怠承認 の 499 行 × 38 列を読み直しています。10 人解除すれば 10 回の全件読取です。ループ外へ出してください。

修正

「検証 → メモリ上で書込内容を全部組み立てる → 最後に一括 setValues」に統一。どうしても途中で失敗しうる箇所は、書込前に _履歴 へ「処理開始」行を残し、復旧の起点にできるようにします。

B-4

現金の残額が支給しても減らない

重要
事実

recordCashOutflow は 04_出金・支給記録!H 残額 に出金額と同じ値を静的に書くだけです（実シートの H6 も数式ではなく値）。markSelectedPaid は 111 行目以降の支給ログに書くだけで、H には触れません。

影響

手許現金と帳簿が突合できません。手渡し給与を扱う以上、ここは事故が起きたときにいちばん見られる欄です。

修正

H を =$C6-SUMIFS($F$111:$F$610,$G$111:$G$610,"現金手渡し") のような式にする（複数回出金するなら出金IDで紐づけ）か、markSelectedPaid 内で減算する。あわせて支給前に「残額 < 支給合計」を検証してください。

B-5

条件に合わない選択行が黙って飛ばされる

重要
事実

closeSelectedPayroll は values[9]（精算予定日）が空、承認済件数 0、既に締め済 の行を filter で除外します。markSelectedPaid と markSelectedReceived も同様。0 件でも「個人締めが完了しました」とトーストが出ます。

影響

担当者は締めたつもりで次に進みます。精算予定日は「未確認の勤怠が残っていると空になる」数式なので、いちばん締めてはいけない人が黙って除外されるのがこの挙動です。

修正

除外理由を件数付きで集計し、ui.alert で提示。処理件数 0 のときは完了トーストを出さない。

B-6

締め済み行の実績編集が履歴に残らない

重要
事実

管理者側 onEdit の締め済み分岐はノートとトーストを出して continue します。appendHistory_ を呼ばず、編集自体も元に戻しません。02_個人別給与 の金額は締め時に凍結済みなので、勤怠と給与が静かに食い違ったまま残ります。

修正

監査上いちばん記録が要る操作です。旧値を e.oldValue から拾って書き戻し、appendHistory_(ss,'締め後編集の拒否', …) を必ず残してください。複数セル編集で oldValue が取れない場合は、少なくとも履歴だけは記録を。

C. 設計・権限・法令

C-1

現場担当者に給与ファイル全体の編集権限が要る

設計
事実

SpreadsheetApp.openById(adminId) は実行したユーザーの権限で動きます。sendConfirmedShifts と markSelectedCleaningCollected（02_個人別給与 の支給状態を読む）を使う現場担当者は、全員の総支給額・源泉所得税・差引支給額が並ぶファイルを開ける必要があります。

修正

管理者アカウント所有の Web アプリ（実行者＝自分／アクセス＝全員）を挟んで書込を仲介するか、逆に管理者側から時間主導トリガでプルする方式へ。後者なら現場ファイルに閲覧権限を与えるだけで済み、実装も軽いです。

C-2

給与明細PDFがスプレッドシートと同じフォルダに作られる

設計
事実

saveBesideSpreadsheet_ は親フォルダに createFile します。PDF はフォルダの共有設定を継承するため、そのフォルダを誰かと共有していれば全員の給与明細が見える状態になります。

修正

明細専用の非共有フォルダIDを _設定 に持ち、そこへ出力。本人へ渡すなら file.addViewer(本人のアドレス) で個別付与し、共有リンクは使わない。

C-3

明細シートの B3 が共有状態になっている

設計
事実

preparePayslipForSelected は 05_給与明細!B3 にスタッフIDを書き、exportPayslipPdf がその表示内容を出力します。2 人が同時に操作すると他人の明細が出ます（04_日別30分配置!B2、05_本人別・配布!B3 も同じ構造）。

修正

PDF化のときだけ一時シートへ複製して出力し、終わったら削除する。あるいは exportSheetPdf_ の前後を LockService で囲み、少なくとも同時操作を直列化してください。

C-4

「同日複数勤務」警告が中抜け勤務を誤検知し、送信を恒常的に止める

設計
事実

警告式の COUNTIFS($B$5:$B$504,$B5,$E$5:$E$504,$E5,$N$5:$N$504,"<>取消")>1 は、同じ日に 2 枠あるだけで必ず警告にします。早番＋遅番の分割勤務は正月では普通の編成です。実際に 08_管理チェック の未対応警告 13 件はすべてこの型でした。

影響

sendConfirmedShifts は「警告が残る確定勤務は送信できません」で全体を止める設計なので、繁忙期に恒常的に送信不能になります。担当者は警告を無視する運用に流れ、本当の警告（18歳未満の深夜など）も見なくなります。

修正

時間帯が実際に重なる場合のみ警告する式へ（SUMPRODUCT で開始日時・終了日時の重なりを判定）。分割勤務は情報レベルに落とし、送信のブロック対象からは外す。ブロックすべきは「担当者未設定」「台帳未一致」「18歳未満の深夜」「休憩不足」に絞るのが実務的です。

C-5

深夜時間帯の定義が二重管理になっている

設計
事実

管理者側 V列は '_設定'!$B$6 / $B$7（22:00 / 5:00）を参照しますが、現場側 U列は TIME(22,0,0) / TIME(5,0,0) のハードコードです。現場 _設定 にも「深夜開始・深夜終了」の行（A6:B7）があるのに使われていません。

修正

現場側 shiftFormula_(21, …) を '_設定'!$B$6 / $B$7 参照へ。設定を変えたのに予定と実績で深夜時間が食い違う、という追跡困難な事故を防げます。

C-6

週40時間超・法定休日の割増が算定されていない

設計
事実

U列は MAX(0, T-8)、つまり日 8 時間超のみです。週 40 時間超、法定休日 35%、月 60 時間超 50% は対象外。深夜と時間外の二重割増（1.25＋0.25）が正しく積み上がる点は良いのですが、週の軸がありません。

影響

12/29〜1/3 のような連続勤務では週 40 時間を超え得ます。短期の巫女でも法定休日を与えていなければ 35% の対象です。

修正

週次集計を入れるのが本筋ですが、少なくとも 06_労務・エラー に「週40時間超の有無を人手で確認する」チェック項目として残し、締め時の警告に含めてください。自動化しないなら、していないことを明示するのが安全です。

C-7

源泉所得税が完全手入力のまま

設計
事実

02_個人別給与!G は空欄で、closeSelectedPayroll は「0円の場合も含めて入力してください」と促すだけ。07_スタッフ・賃金 の 源泉区分は全員「未判定」、扶養控除申告は「未確認」、雇用保険は「要確認」のままです。

修正

日々雇い入れる巫女なら日額表・丙欄の適用対象です。丙欄の税額表を _設定 に持たせ、差引支給額の日額 から自動算出したうえで手動上書きを許す形が現実的。少なくとも源泉区分が「未判定」の人は締められないようにしてください。現状は未判定でも締められます。

C-8

タイムゾーンのフォールバックが効いていない

設計
事実

Session.getScriptTimeZone() || 'Asia/Tokyo' は、getScriptTimeZone() が常に非空を返すため フォールバックが発動しません。プロジェクトのタイムゾーンがずれていれば、締めID・支給ID・履歴の日時が全部ずれます。

修正

両方の appsscript.json に "timeZone": "Asia/Tokyo" を明示。2 ファイルで違うと日跨ぎ勤務の日付境界が食い違います。
