# 巫女勤怠・給与スクリプト 実シート突合レビュー

対象:

- 管理者用 `巫女勤怠・給与管理（再構築版・完成）` — `1GOBCBElaR586D6roa4_JlHfl3Sup5XR3KGAcaXYbYGM`
- 現場用 `巫女シフト・現場運営（再構築版・完成）` — `1jIb8Z72DsSJc-92iHvMSm_5K7JcS1ESZPT3AEj4MZ2E`

検証方法: 両ファイルを xlsx として書き出し、各シートのヘッダ行・数式・実データを
スクリプトの前提と 1 列ずつ突合した。行位置（勤怠 5〜503 / 個人別 5〜204 /
出金 6〜106 / 支給ログ 111〜610 / 台帳 25〜224）、`03_本日の最終日精算!B3`、
`05_給与明細!B3・D3・A11`、`_設定!B4〜B7`、現場 `_設定!F2・H2・F3・H3・J3`、
管理者側 `T〜AB` の計算式はすべてコードと一致していた。ズレていたのは以下の箇所のみ。

---

## 結論

現在のコードのままでは、承認も締めも支給も 1 件も通らない。個別のバグではなく、
現場→管理の連携パイプラインが 4 箇所で切れている。

1. 送信すると `01_勤怠承認!C（スタッフID）` に「本堂1｜早番 9:00～15:00」というシフト名が入る（A-1）
2. スタッフIDが一致しないので `R 確定基本時給` の INDEX/MATCH が空になり、承認時に「時給が未設定です」で停止
3. 仮に時給が入っても `AL 実績連携` が「未送信」のまま。これを「実績送信済」にする処理がどちらのスクリプトにも存在しない（A-2）
4. 承認が 0 件なので `02_個人別給与` の COUNTIFS/SUMIFS は全員 0 円。締め条件（承認済件数>0）を満たす人が出ない

## 設計として良くできている点

- **承認時に時給・交通費を静的値へ固定する設計。** `07_スタッフ・賃金` を後日改定しても
  過去の承認済み給与が動かない。締め時に `T〜AB` を凍結するのも同じ思想で一貫している。
- **状態機械と解除の作法。** 未確認→承認済→締め済→支給済→受領済 の一方向遷移、
  解除には理由入力を必須にして `_履歴` へ残す。監査に耐える骨格。
- **部分適用を避ける意識。** `approveSelectedAttendance` が「全行検証 → 全行書込」の順、
  空き行不足を書込み前に検出、締め済み行への上書きを現場側から拒否。
- **深夜時間の計算式。** 「当日22時〜翌5時」と「当日0時〜5時」の 2 区間の重なりで取る式は
  正しく、23:00→翌06:00 で 6.0h を返す。除算前に分へ丸めているのも良い。
- **法令値に適用開始日と出典URLを持たせている。**

## A. 致命的 — これを直さないと動かない

### A-1. スタッフIDの代わりにシフト名を送っている

`02_シフト入力` の実列は **C＝シフト名（自動）**、**E＝スタッフID**。
`sendConfirmedShifts` は `r[2]`（＝C列）を送信先の「スタッフID」列に書いている。

影響: `_取込!C` と `01_勤怠承認!C` にシフト名が入る。E区分・R確定基本時給・
S確定交通費の INDEX/MATCH がすべて外れ、`02_個人別給与` の集計も 0 のまま。

```js
// sendConfirmedShifts の pending.forEach 内。冒頭で E列を取る
const staffId = String(r[4] || '').trim();   // E列＝スタッフID

imported.getRange(importRow, 1, 1, 15).setValues([[
  workId, r[1], staffId /* was r[2] */, r[3], r[5], r[6], r[7], r[9], r[14], r[13],
  now, user, '取込済', r[10] || '通常', sourceUpdated
]]);

// 新規行
attendance.getRange(attendanceRow, 1, 1, 4).setValues([[workId, r[1], staffId, r[3]]]);
// 既存行の更新
attendance.getRange(attendanceRow, 2, 1, 3).setValues([[r[1], staffId, r[3]]]);
```

あわせて送信前の検証に「確定なのに E列が空（台帳未一致）の行は送らない」を追加する。

### A-2. 当日実績を送る処理が存在しない（承認が永久に通らない）

`approveSelectedAttendance` は `AL 実績連携` が `'実績送信済'` でなければ throw する。
実シートの既存 2 行はどちらも「未送信」。現場ファイルには `02A_当日勤怠`
（A〜S列、H＝実績状態、R＝給与連携）があるが、貼られたスクリプトはこのシートを
一度も参照していない。`sendConfirmedShifts` が送るのは予定シフトだけ。

二次被害: 管理者側 `onEdit` は承認後に実績を編集すると `AL` に `'変更あり'` を書く。
`'実績送信済'` に戻す処理がないため、一度修正した行は二度と承認できない。

修正: 現場側に `sendActualResults()` を新設。突合キーは勤務ID。

```
// 02A_当日勤怠 → 01_勤怠承認 の対応
I 実出勤    → I (9)       J 実退勤   → J (10)
K 実休憩    → K (11)      N 変更理由 → AI (35)
P 現場確認者 → AJ (36)     Q 確認日時 → AK (37)

// H 実績状態 → O 承認状態
'勤務済'   → '未確認'   （管理者がこれから承認する）
'欠勤確定' → '欠勤確定'
'事前取消' → '事前取消'

// 最後に両側のフラグを立てる
attendance.getRange(row, 38).setValue('実績送信済');  // AL
genba.getRange(r, 18).setValue('実績送信済');          // 02A の R列
```

送信条件は `02A!S 警告` が空（現状は「実績未入力・」が立っている）かつ
`H 実績状態` が「未入力」以外。承認済・締め済の行は拒否する。

onEdit の片道切符も同時に解消する。管理者が実績を直したのは正当な修正なので
`'変更あり'` ではなく `'管理者修正'` を書き、承認側の判定を
`['実績送信済','管理者修正'].indexOf(...) === -1` に緩める。

### A-3. 襦袢台帳の列番号が実シートと全部ずれている

`06_食事・貸与` の実際の台帳は 24 行目がヘッダ、25〜224 行がデータ（行は合っている）。
列は **A スタッフID / B 氏名 / C 襦袢 / D 貸出状態 / E 返却状態 / F 直接回収状態 /
G 回収日時 / H 回収担当 / I 備考** の 9 列で、J 以降は空。

影響: `markSelectedJubanLoaned` は E・F（返却状態・直接回収状態）に「貸出済／未返却」を
書き込み台帳を壊す。`markSelectedJubanReturned` の `values[4] !== '貸出済'` は
E（返却状態）を見るので常に例外。`markSelectedCleaningCollected` の書込先 N・O・Q は
すべて空列。保護範囲 `N25:Q224` も空列を守っている。

| 用途 | スクリプトの前提 | 実シート | 修正 |
|---|---|---|---|
| 襦袢（貸与/持参） | C | C | `values[2]` そのまま |
| 貸出状態 | E | D | `values[4]` → `values[3]` |
| 返却状態 | F | E | `values[5]` → `values[4]` |
| 直接回収状態 | N | F | `values[13]` → `values[5]` |
| 回収日時 | O | G | `values[14]` → `values[6]` |
| 回収担当 | Q (17) | H (8) | 書込列 `17` → `8` |

```js
const LEDGER_COL = Object.freeze({
  STAFF_ID:1, NAME:2, JUBAN:3, LOAN:4, RETURN:5,
  COLLECT:6, COLLECTED_AT:7, COLLECTOR:8, NOTE:9
});

// 貸出       getRange(row, 4, 1, 2).setValues([['貸出済','未返却']]);   // was 5
// 回収欄初期化 getRange(row, 6, 1, 4).setValues([['未回収','','','']]);   // was 14
// 返却       getRange(row, 5).setValue('返却済');                       // was 6
// 回収記録    getRange(row, 6, 1, 2).setValues([['回収済', now]]);        // was 14
//            getRange(row, 8).setValue(user);                          // was 17
// 保護       ensureWarningProtection_(ledger, 'F25:I224', …);           // was N25:Q224
// handleLedgerEdit_ の列ガードも 5/6/14/17 → 4/5/6/8 へ
```

### A-4. 勤務IDが行番号依存で、2 ファイルの採番規則も食い違っている

`02_シフト入力!A` は `"WK-"&TEXT($B,"yyyymmdd")&"-S"&TEXT(ROW()-4,"000")`、つまり
**行番号**でIDを作る（実データ: `WK-20261229-S001`）。一方 `01_勤怠承認` と
`02A_当日勤怠` の実データは**スタッフID基準**の `WK-20261231-M004-001`。
同じ「勤務ID」という名前で 2 つの体系が並走している。

影響: 送信済み行のIDは静的値に固定されるが、未送信行は行番号から再計算される。
行を 1 行削除するだけで固定済みIDと数式IDが衝突し、`assertUniqueWorkIds_` が
全体を止める。並べ替え・フィルタ後の行挿入も同様。

修正: IDは数式で作らず、送信時にスクリプトが採番して静的値で確定させる。
既存データに合わせるなら `WK-{yyyymmdd}-{スタッフID}-{その人その日の連番}`。
未送信行のA列は数式ではなく空欄か「未採番」表示にし、
`repairShiftFormulasOnSheet_` がA列を書き戻す処理は削除する。

## B. 重要 — 運用が止まる / データが壊れる

### B-1. 500 行の上限に正月編成が収まらない

`02_シフト入力` は 5〜504 行の 500 行。現状 **12/29〜1/1 の 4 日間だけで
担当者入力済 138 行**、最終行は 142 行目。`_設定` の対象期間は 12/29〜1/31（34 日間）。
同じ密度なら 1,000 行を超える。`01_勤怠承認` も 5〜503 行で同じ天井。

`nextBlankRow_` が「空き行がありません」で throw し、送信も承認も不能になる。
しかも満杯になるのは元日直前。

修正: 行数を 2,000 行程度まで拡張し、`FIELD.LAST_ROW` / `PAY_ROW.*` を
`sheet.getMaxRows()` から動的に求める。数式の参照範囲（`$B$5:$B$504` 等）も同時に伸ばす。

### B-2. onEdit が重すぎて簡易トリガの 30 秒制限に当たる

現場側 `onEdit` は編集行ごとに `repairShiftFormulasOnSheet_`（10 列 × setFormulas ＋
ID列の読み書き）を呼び、さらに 1 セルずつ `getDisplayValue()` している。
管理者側も 1 行あたり 38 列読取＋最大 6 回の書込＋`appendHistory_`
（`_履歴` の全行スキャン）。

数十行を貼り付けると数百〜数千回の API 呼び出しになり 30 秒上限を超える。
途中で落ちるため、一部の行だけ数式が復元され一部は生値のまま、という状態が残る。

修正: ①編集範囲が自動列に掛かったときだけ数式復元を走らせる（現状は 21 列すべてで発動）
②行ループ内の `getRange` を範囲一括の `getValues`/`setValues` に置換
③`appendHistory_` は `getLastRow()+1` か `appendRow` で末尾追記し、複数行分は 1 回の
`setValues` にまとめる。

### B-3. 例外が書込ループの途中で投げられ、部分適用が残る

`sendConfirmedShifts` の書込ループ内に締め済チェックの `throw` が残っている
（事前チェック済みでも、他の人が同時に締めれば発生する）。Apps Script に
ロールバックはないため、前半の行だけ管理者側へ同期された状態で止まる。

`releaseSelectedClose` は 1 件ごとに `01_勤怠承認` の 499 行 × 38 列を読み直している。
ループ外へ出す。

修正: 「検証 → メモリ上で書込内容を全部組み立てる → 最後に一括 `setValues`」に統一。

### B-4. 現金の残額が支給しても減らない

`recordCashOutflow` は `04_出金・支給記録!H 残額` に出金額と同じ値を静的に書くだけ
（実シートの H6 も数式ではなく値）。`markSelectedPaid` は 111 行目以降の支給ログに
書くだけで H には触れない。手許現金と帳簿が突合できない。

修正: H を `=$C6-SUMIFS($F$111:$F$610,$G$111:$G$610,"現金手渡し")` のような式にするか、
`markSelectedPaid` 内で減算する。あわせて支給前に「残額 < 支給合計」を検証する。

### B-5. 条件に合わない選択行が黙って飛ばされる

`closeSelectedPayroll` は `values[9]`（精算予定日）が空、承認済件数 0、既に締め済 の行を
`filter` で除外する。`markSelectedPaid` と `markSelectedReceived` も同様。
0 件でも「個人締めが完了しました」とトーストが出る。

精算予定日は「未確認の勤怠が残っていると空になる」数式なので、
いちばん締めてはいけない人が黙って除外されるのがこの挙動。

修正: 除外理由を件数付きで集計し `ui.alert` で提示。処理件数 0 のときは完了トーストを出さない。

### B-6. 締め済み行の実績編集が履歴に残らない

管理者側 `onEdit` の締め済み分岐はノートとトーストを出して `continue` する。
`appendHistory_` を呼ばず、編集自体も元に戻さない。`02_個人別給与` の金額は
締め時に凍結済みなので、勤怠と給与が静かに食い違ったまま残る。

修正: 旧値を `e.oldValue` から拾って書き戻し、
`appendHistory_(ss,'締め後編集の拒否', …)` を必ず残す。

## C. 設計・権限・法令

### C-1. 現場担当者に給与ファイル全体の編集権限が要る

`SpreadsheetApp.openById(adminId)` は実行したユーザーの権限で動く。
`sendConfirmedShifts` と `markSelectedCleaningCollected`（`02_個人別給与` の
支給状態を読む）を使う現場担当者は、全員の総支給額・源泉所得税・差引支給額が
並ぶファイルを開ける必要がある。

修正: 管理者アカウント所有の Web アプリ（実行者＝自分／アクセス＝全員）を挟んで
書込を仲介するか、逆に管理者側から時間主導トリガでプルする方式へ。
後者なら現場ファイルに閲覧権限を与えるだけで済む。

### C-2. 給与明細PDFがスプレッドシートと同じフォルダに作られる

`saveBesideSpreadsheet_` は親フォルダに `createFile` する。PDF はフォルダの共有設定を
継承するため、そのフォルダを誰かと共有していれば全員の給与明細が見える。

修正: 明細専用の非共有フォルダIDを `_設定` に持ちそこへ出力。
本人へ渡すなら `file.addViewer(本人のアドレス)` で個別付与し、共有リンクは使わない。

### C-3. 明細シートの B3 が共有状態になっている

`preparePayslipForSelected` は `05_給与明細!B3` にスタッフIDを書き、
`exportPayslipPdf` がその表示内容を出力する。2 人が同時に操作すると他人の明細が出る
（`04_日別30分配置!B2`、`05_本人別・配布!B3` も同じ構造）。

修正: PDF化のときだけ一時シートへ複製して出力し、終わったら削除する。
あるいは `exportSheetPdf_` の前後を `LockService` で囲む。

### C-4. 「同日複数勤務」警告が中抜け勤務を誤検知し、送信を恒常的に止める

警告式の `COUNTIFS($B$5:$B$504,$B5,$E$5:$E$504,$E5,$N$5:$N$504,"<>取消")>1` は、
同じ日に 2 枠あるだけで必ず警告にする。早番＋遅番の分割勤務は正月では普通の編成。
実際に `08_管理チェック` の未対応警告 13 件はすべてこの型だった。

`sendConfirmedShifts` は「警告が残る確定勤務は送信できません」で全体を止める設計なので、
繁忙期に恒常的に送信不能になる。担当者は警告を無視する運用に流れ、
本当の警告（18歳未満の深夜など）も見なくなる。

修正: 時間帯が実際に重なる場合のみ警告する式へ（`SUMPRODUCT` で開始日時・終了日時の
重なりを判定）。分割勤務は情報レベルに落とし、送信のブロック対象からは外す。
ブロックすべきは「担当者未設定」「台帳未一致」「18歳未満の深夜」「休憩不足」に絞る。

### C-5. 深夜時間帯の定義が二重管理になっている

管理者側 V列は `'_設定'!$B$6 / $B$7`（22:00 / 5:00）を参照するが、現場側 U列は
`TIME(22,0,0)` / `TIME(5,0,0)` のハードコード。現場 `_設定` にも「深夜開始・深夜終了」の
行（A6:B7）があるのに使われていない。

修正: 現場側 `shiftFormula_(21, …)` を `'_設定'!$B$6 / $B$7` 参照へ。

### C-6. 週40時間超・法定休日の割増が算定されていない

U列は `MAX(0, T-8)`、つまり日 8 時間超のみ。週 40 時間超、法定休日 35%、
月 60 時間超 50% は対象外。深夜と時間外の二重割増（1.25＋0.25）が正しく積み上がる点は
良いが、週の軸がない。12/29〜1/3 のような連続勤務では週 40 時間を超え得る。

修正: 週次集計を入れるのが本筋。少なくとも `06_労務・エラー` に
「週40時間超の有無を人手で確認する」チェック項目として残し、締め時の警告に含める。

### C-7. 源泉所得税が完全手入力のまま

`02_個人別給与!G` は空欄で、`closeSelectedPayroll` は「0円の場合も含めて入力してください」と
促すだけ。`07_スタッフ・賃金` の源泉区分は全員「未判定」、扶養控除申告は「未確認」、
雇用保険は「要確認」のまま。

修正: 日々雇い入れる巫女なら日額表・丙欄の適用対象。丙欄の税額表を `_設定` に持たせ、
差引支給額の日額から自動算出したうえで手動上書きを許す。少なくとも源泉区分が
「未判定」の人は締められないようにする（現状は未判定でも締められる）。

### C-8. タイムゾーンのフォールバックが効いていない

`Session.getScriptTimeZone() || 'Asia/Tokyo'` は `getScriptTimeZone()` が常に非空を返すため
フォールバックが発動しない。プロジェクトのタイムゾーンがずれていれば、締めID・支給ID・
履歴の日時が全部ずれる。

修正: 両方の `appsscript.json` に `"timeZone": "Asia/Tokyo"` を明示。

## D. コード品質

- **2 本は必ず別プロジェクトに。** `onOpen` `onEdit` `requireSheet_` `formatDate_`
  `safeName_` `nextBlankRow_` `countBlankRows_` `selectedDataRows_` `withDocumentLock_`
  `activeUser_` `exportSheetPdf_` `saveBesideSpreadsheet_` `showCreatedFile_`
  `ensureWarningProtection_` `requireActiveSheet_` が同名で重複している。
  1 つのプロジェクトに貼ると後勝ちで静かに壊れる。
- **管理者側 `setupAndCheck` の必須シート一覧に `_設定` がない。**
  `T〜AB` 列の数式が `'_設定'!$B$4〜$B$7` を参照している。
- **定数を定義しながら使っていない箇所が多数。** `selectedDataRows_(sheet, 5, 503)`、
  `getRange(5, 1, 499, 38)`、`nextBlankRow_(sheet, 6, 106, 1)` など。
  `PAY_ROW` / `PERSONAL_COL` に寄せる。行数変更（B-1）のときに漏れる。
- **管理者側に「数式修復」メニューがない。** 承認・締めの解除で復元されるのは一部の列だけで、
  `E` `AD` `AE` `AG` `AH` や未処理行の `T〜AB` は壊れたら手作業。
- **`appendHistory_` が満杯で throw する。** `_履歴` の空き行が尽きると全操作が停止する。
  `appendRow` か `insertRowsAfter` で自動拡張を。ID の `LOG-…-SSS` もループ内では
  同一ミリ秒の衝突余地があるので行番号を足す。
- **`exportSheetPdf_` にステータス確認がない。** `muteHttpExceptions:true` と
  `getResponseCode()===200` の判定を。現状はエラーHTMLがそのまま `.pdf` として保存され得る。
  `range` 未指定なので空行まで出力される。
- **保護がすべて `setWarningOnly(true)`。** 警告を出すだけで数式の誤上書きは止められない。
  自動列だけでも編集者を限定した本保護にする価値がある。
- **`waitLock(30000)` の失敗が英語の例外になる。** try/catch して日本語メッセージに。
  メニュー関数全体を `runSafely_` でくるみ `ui.alert` を出す形にすると現場が楽になる。
- **`activeUser_()` が組織外アカウントで空文字を返す。** 「利用者」のまま `_履歴` に
  残ると監査にならない。取得できない場合は担当者名の入力を必須にする。
- **`_設定!J3` の管理者ファイルIDが平文。** 現場ファイルの編集者なら誰でも書き換えられる。
  `PropertiesService.getScriptProperties()` へ。
- **未使用コード。** 管理者側 `attendanceDates_`、現場側 `idRowIndex_`、
  `approveSelectedAttendance` の検証ループ内 `workId`。
