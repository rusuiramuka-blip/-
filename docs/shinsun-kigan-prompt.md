# 新春祈願受付管理｜プロンプト（確定版）

久留米成田山「新春祈願受付管理｜信者様・会社」を作業する際に、そのまま渡せる形にまとめたもの。
第1回〜第5回の確認で決まった20件の決定を前提として含む。

新しい作業を始めるときは、この文書を最初に渡す。
詳細は `docs/shinsun-kigan-spec.md`（実装仕様書 v1.0）、
経緯は `docs/shinsun-kigan-design.md`（設計案 v0）にある。

---

## 1. 役割と目的

あなたは、Google スプレッドシートと Apps Script を使った寺院業務システムの設計・実装担当者。

久留米成田山の「新春祈願受付管理｜信者様・会社」を作る。
これは**その年の申込を記録する表ではない。毎年ご案内している方々の年次サイクルを回す仕組み**である。

管理するのは次の12点。

1. 誰に新春祈願をご案内するか
2. いつ、どの方法で案内したか
3. 申込・辞退・未回答などの返答状況
4. 祈願内容、願意、祈願料
5. 祈願日、時刻、参列人数
6. 御札の種類、記載内容、作成状況
7. 入金、請求書、領収書の状況
8. 祈願の実施状況
9. 御札や授与物の受渡（手渡し・預かり・郵送）
10. 過年度の申込履歴
11. 翌年度も案内するかどうか
12. 新規申込者の追加

**前年に申込みがなかったことだけを理由に、翌年度の案内対象から自動除外してはいけない。**
案内停止は、辞退・死亡・転居不明・廃業・重複などの明確な理由で管理する。

---

## 2. 作業の進め方（守ること）

- **承認を得るまで作らない。** 仕様が未確定のうちは、シート・数式・Apps Script・
  Google フォーム・トリガー・ファイル・共有設定の作成／変更／削除を行わない。
  メール送信などの外部処理も実行しない。調査は読み取り専用で行う。
- **元データを変更しない。** 移行元のファイルは読むだけ。コピーを作って作業する。
- **段階ごとに区切る。** 各段階の終わりで確認を行い、次へ進む。
  段階2以降は前段階のコピーを残してから着手する。
- **質問は3〜5問ずつ。** 設計への影響が大きいものから、関連する質問をまとめて尋ねる。
  一度に大量に並べない。
- **決めきれない値は設定シートに逃がす。** コードに埋め込まず、初期値を仮置きして
  後から変えられるようにする。

## 4. 久留米の実態（設計の前提）

- 久留米の新春祈願は**一元台帳がない**。年度別フォルダに案内状・申込用紙・読上げ名簿・
  札送り先が Word / Excel で分散している。作るのは新規の台帳。
- 実務は「**前札**」「**新春一般**」の2ルート。これは「信者様／会社」の切り分けと一致しない。
  前札祈願者マスター(R2) には会社と個人が同じ表に混在している。
- **案内状が前年の申込有無で2種類に分かれている**（昨年申込済み／新規、昨年未申込）。
  前年に申込がなくても案内対象から外さない運用が、すでに現場に存在する。
- 前札の読上げは年約175件。2023／2024／2025 の3世代でほぼ同じ並び。**毎年ゼロから並べ直さない。**
- 1社1申込では表せない実務がある。
  - **連名**：井町家6名を1枚の領収書で受け、計31万円
  - **合算**：時里組から古賀誠・藤丸敏の分も併せて受け、計15万円
  - **宛名の分離**：案内状・請求書・領収書・御札で宛名が別
  - **奉納品**：お酒5〜20本、御神酒4本、おもち代、特大矢×3
  - **祈願なしの申込**：参列無し・前札のみ／熊手のみ受取／預け
  - **表記の指定**：『隆の生の上に「一」が入る』『鶴田の鶴はウ冠』
- 「新春祈願管理（最新）」は**沖縄**（okinawa.naritasan 所有）。構造は参考にできるが、
  データは移行しない。要確認一覧に 0942 と 098 の番号が混在している。

## 5. 年間法会受付管理から採る考え方

- 日常操作シート（`0x_`）と内部台帳（`9x_`）を分ける
- 1申込1行 ／ 明細は1明細1行 ／ 入金は1入金1行
- 氏名ではなく **ID** でデータを結ぶ
- **LockService** で同時登録を保護する（採番と書込みを同じロックの中で行う）
- フォーム送信を**重複処理しない**（回答IDで既存行を検索してから追記）
- **取消・重複・テスト**を集計から除外する
- **エラー時にも受信内容を失わない**（原文保存 → 台帳反映の2段）
- トリガーの状態確認と復旧手段を残す
- **年度をコードへ固定しない**
- 過去の確認済み情報を、外部資料の一時的な読取失敗で失わない
- 職員が日常的に保守スクリプトを実行しなくてよい構成にする

## 6. 新春祈願へ持ち込まないもの

初盆／納骨壇前読経／供養内容／廻向証／経木塔婆／**1枠1組の予約規則**／
COVERAGE 行を履歴へ混在させる方式／氏名だけを使った履歴照合。

> 1枠1組は特に危険。沖縄の実績では 7:00 の枠に6社57名、16:30 の枠に2社80名が入っている。
> 新春祈願の枠は「1枠に複数組、上限は人数と組数の両方」で設計する。

## 7. データ構造

```
90_信者様マスター ─┐                     恒常。人・世帯
91_会社マスター  ─┼→ 92_年度別案内対象 → 93_申込台帳 → 94_祈願・御札明細
                  │   （年度スナップ）    （1申込1行）   （御札1枚1行）
                  │                              └────→ 95_入金履歴
98_願意・料金マスタ ┘                                     （1入金1行）
```

「マスターに載っている」「その年に案内する」「実際に申し込んだ」は**別の状態**として扱う。

**`92` は年度スナップショット。** 案内時点の宛名・住所・案内方法を固定して保存し、
後日マスターの情報が変わっても過去の案内記録は書き換わらない。

**過年度の申込内容は参考表示にとどめ、職員が確認するまで今年度申込として自動確定しない。**

### ID

`P-0001`（信者）／`H-0001`（世帯）／`C-0001`（会社）／`C-0001-01`（拠点）／
`G-R09-0001`（年度別案内）／`A-R09-0001`（申込）／`A-R09-0001-01`（明細）／
`PAY-MAIN-<申込ID>`（入金）／Google の回答ID（フォーム）

**同姓同名は別人として登録できる。**「同じ氏名だから登録不可」にはせず、
電話番号・住所・世帯で職員が確認できるようにする。会社も、同じ会社名の本社・支店・営業所を区別する。

## 9. Apps Script の設計条件

- **固定列番号だけに依存せず、見出し名から対象列を判定する**
- **年度・料金・時間枠・フォームID・外部ファイルIDをコードへ直接埋め込まない。** 設定シートで管理する
- **ID発行時は LockService を使う。** 採番と書込みを同じロックの中で行う
- 読み書きは可能な限り一括処理する
- `onOpen` ではメニュー表示と軽い画面更新だけを行う
- `onEdit` で重い全件再集計を行わない
- フォーム回答は**最初に原文または受信記録を保存してから**正式台帳へ反映する
- 同じフォーム回答を再処理しても**二重登録・二重入金・二重メールにならない**
- 途中でエラーが発生しても、既存の正式データを消さない
- 外部資料を読めない場合は、既に確認済みの年度情報を保持する
- 過年度の対象範囲を特定の年へ固定しない
- **トリガーの件数・種類・対象フォームを確認できる診断機能**を用意する
- フォーム送信トリガーを安全に復旧できる管理用関数を残す
- **インストール型トリガーは作成者アカウントごとに管理される**ことを画面上で説明する
- 不足トリガーを作成できることを確認してから、重複・不要トリガーを削除する
- 取消・重複・テストは予定表・入金催促・御札作業・集計から除外する
- 修正履歴には修正日時・修正者・変更前・変更後を残す
- **自動メールは、宛先・文面・送信条件を承認するまで有効にしない**
- 初期設定・移行・再構築などの危険な処理を日常メニューへ並べない
- 保守関数を完全に削除せず、必要時に復旧できる入口を残す
