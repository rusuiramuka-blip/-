新春祈願受付管理
プロンプト

久留米成田山「新春祈願受付管理｜信者様・会社」を作業するとき、そのまま渡せる形にまとめたものです。第1回〜第5回の確認で決まった20件の決定を前提として含みます。詳細は実装仕様書 v1.0、経緯は設計案 v0 にあります。

役割と目的

Google スプレッドシートと Apps Script を使った寺院業務システムの設計・実装を担当します。

作るのはその年の申込を記録する表ではありません。毎年ご案内している方々の年次サイクルを回す仕組みです。

管理する12点

#管理するもの#管理するもの
1誰に案内するか7入金・請求書・領収書
2いつ、どの方法で案内したか8祈願の実施状況
3申込・辞退・未回答の返答状況9受渡（手渡し・預かり・郵送）
4祈願内容・願意・祈願料10過年度の申込履歴
5祈願日・時刻・参列人数11翌年度も案内するか
6御札の種類・記載内容・作成状況12新規申込者の追加

前年に申込みがなかったことだけを理由に、翌年度の案内対象から自動除外してはいけません。案内停止は、辞退・死亡・転居不明・廃業・重複などの明確な理由で管理します。

作業の進め方

  • 承認を得るまで作らない仕様が未確定のうちは、シート・数式・Apps Script・Google フォーム・トリガー・ファイル・共有設定の作成／変更／削除を行いません。メール送信などの外部処理も実行しません。調査は読み取り専用で行います。
  • 元データを変更しない移行元のファイルは読むだけ。コピーを作って作業します。
  • 段階ごとに区切る各段階の終わりで確認を行い、次へ進みます。段階2以降は前段階のコピーを残してから着手します。
  • 質問は3〜5問ずつ設計への影響が大きいものから、関連する質問をまとめて尋ねます。一度に大量に並べません。
  • 決めきれない値は設定シートに逃がすコードに埋め込まず、初期値を仮置きして後から変えられるようにします。

久留米の実態（設計の前提）

  • 一元台帳がない年度別フォルダに案内状・申込用紙・読上げ名簿・札送り先が Word / Excel で分散しています。作るのは新規の台帳です。
  • 実務は「前札」「新春一般」の2ルートこれは「信者様／会社」の切り分けと一致しません。前札祈願者マスター(R2) には会社と個人が同じ表に混在しています。
  • 案内状が前年の申込有無で2種類に分かれている昨年申込済み／新規（昨年未申込）。前年に申込がなくても案内対象から外さない運用が、すでに現場に存在します。
  • 前札の読上げは年約175件2023／2024／2025 の3世代でほぼ同じ並び。毎年ゼロから並べ直しません。
  • 1社1申込では表せない実務がある連名：井町家6名を1枚の領収書で受け計31万円／合算：時里組から古賀誠・藤丸敏の分も併せて計15万円／宛名の分離：案内状・請求書・領収書・御札で宛名が別／奉納品：お酒5〜20本、御神酒4本、おもち代、特大矢×3／祈願なしの申込：参列無し前札のみ・熊手のみ受取・預け／表記の指定：『隆の生の上に「一」が入る』『鶴田の鶴はウ冠』
  • 「新春祈願管理（最新）」は沖縄のファイル構造は参考にできますが、データは移行しません。要確認一覧に 0942 と 098 の番号が混在しています。

年間法会受付管理から採る／採らない

採る考え方

  • 日常操作シート（0x_）と内部台帳（9x_）を分ける
  • 1申込1行／明細は1明細1行／入金は1入金1行
  • 氏名ではなく ID でデータを結ぶ
  • LockService で同時登録を保護する（採番と書込みを同じロックの中で行う）
  • フォーム送信を重複処理しない（回答IDで既存行を検索してから追記）
  • 取消・重複・テストを集計から除外する
  • エラー時にも受信内容を失わない（原文保存 → 台帳反映の2段）
  • トリガーの状態確認と復旧手段を残す
  • 年度をコードへ固定しない
  • 過去の確認済み情報を、外部資料の一時的な読取失敗で失わない
  • 職員が日常的に保守スクリプトを実行しなくてよい構成にする

持ち込まないもの

初盆／納骨壇前読経／供養内容／廻向証／経木塔婆／1枠1組の予約規則／COVERAGE 行を履歴へ混在させる方式／氏名だけを使った履歴照合。

1枠1組は特に危険です。沖縄の実績では 7:00 の枠に6社57名、16:30 の枠に2社80名が入っています。新春祈願の枠は「1枠に複数組、上限は人数と組数の両方」で設計します。

データ構造

90_信者様マスター ─┐                     恒常。人・世帯
91_会社マスター  ─┼→ 92_年度別案内対象 → 93_申込台帳 → 94_祈願・御札明細
                  │   （年度スナップ）    （1申込1行）   （御札1枚1行）
                  │                              └────→ 95_入金履歴
98_願意・料金マスタ ┘                                     （1入金1行）
  • 3つの状態を区別する「マスターに載っている」「その年に案内する」「実際に申し込んだ」は別の状態です。
  • 92 は年度スナップショット案内時点の宛名・住所・案内方法を固定して保存し、後日マスターの情報が変わっても過去の案内記録は書き換わりません。
  • 過年度の申込内容は参考表示にとどめる職員が確認するまで、今年度申込として自動確定しません。
  • 同姓同名は別人として登録できる「同じ氏名だから登録不可」にはせず、電話番号・住所・世帯で職員が確認できるようにします。会社も、同じ会社名の本社・支店・営業所を区別します。

ID

P-0001（信者）／H-0001（世帯）／C-0001（会社）／C-0001-01（拠点）／G-R09-0001（年度別案内）／A-R09-0001（申込）／A-R09-0001-01（明細）／PAY-MAIN-<申込ID>（入金）／Google の回答ID（フォーム）

Apps Script の設計条件

  • 固定列番号だけに依存せず、見出し名から対象列を判定する
  • 年度・料金・時間枠・フォームID・外部ファイルIDをコードへ直接埋め込まない。設定シートで管理する
  • ID発行時は LockService を使う。採番と書込みを同じロックの中で行う
  • 読み書きは可能な限り一括処理する
  • onOpen ではメニュー表示と軽い画面更新だけを行う
  • onEdit で重い全件再集計を行わない
  • フォーム回答は最初に原文または受信記録を保存してから正式台帳へ反映する
  • 同じフォーム回答を再処理しても二重登録・二重入金・二重メールにならない
  • 途中でエラーが発生しても、既存の正式データを消さない
  • 外部資料を読めない場合は、既に確認済みの年度情報を保持する
  • 過年度の対象範囲を特定の年へ固定しない
  • トリガーの件数・種類・対象フォームを確認できる診断機能を用意する
  • フォーム送信トリガーを安全に復旧できる管理用関数を残す
  • インストール型トリガーは作成者アカウントごとに管理されることを画面上で説明する
  • 不足トリガーを作成できることを確認してから、重複・不要トリガーを削除する
  • 取消・重複・テストは予定表・入金催促・御札作業・集計から除外する
  • 修正履歴には修正日時・修正者・変更前・変更後を残す
  • 自動メールは、宛先・文面・送信条件を承認するまで有効にしない
  • 初期設定・移行・再構築などの危険な処理を日常メニューへ並べない
  • 保守関数を完全に削除せず、必要時に復旧できる入口を残す
