# 新春祈願受付管理｜信者様・会社　設計案 v0

久留米成田山の新春祈願を、**その年の申込記録ではなく「毎年ご案内する方々の年次サイクル」**として
管理するための設計。実装前の調査結果・構成案・未確定事項をまとめる。

> この文書の時点では、シート・数式・Apps Script・フォーム・トリガー・共有設定の
> 作成／変更／削除は一切行っていない。すべて読み取り専用の調査に基づく。

## 0. 決定事項（第1回）

| # | 論点 | 決定 |
|---|---|---|
| ① | 区分の切り方 | **属性で分ける**。`90_信者様マスター` と `91_会社マスター`。前札／新春一般は**申込側の属性**（`92` の案内ルート、`93` の申込区分）として持つ |
| ② | 住所・電話・メールの正本 | **この新春祈願管理表**。らくまる寺務からの取込は行わない |
| ③ | 祈願札区分・願意マスタ | **現行「祈願申込入力」と共有**（9区分・38願意）。願意は**正式名称**で持つ |
| ④ | 移行する過去年度 | **見つかった分だけ**。R2 前札マスター＋読上げ名簿 2023／2024／2025。R9 から新台帳で運用開始 |

### ①の帰結

- 前札マスター(R2) の約170件は、移行時に**個人と会社へ振り分ける**（職員確認が必要な工程）。
- 「前札」「新春一般」は `92_年度別案内対象` の**案内ルート**列と、`93_申込台帳` の**申込区分**列で表す。
  同じ方が前札と一般の両方に載ることも、データ上は自然に表現できる。
- 案内状の種類（昨年申込済み／新規）は、ルート×前年申込有無から**自動判定**する。

### ②の帰結

- `90`／`91` に郵便番号・住所・建物名・電話・メールを**実列として持つ**（数式や外部参照にしない）。
- 年間法会受付管理の一般信者名簿と**同じ方の住所が2箇所に存在しうる**。
  当面は同期しない。将来そろえる場合に備え、`90` に「年間法会の人物ID」列を任意項目として用意しておく。
- `92` は引き続き案内時点のコピーを持つ。正本が手元にあっても、過去の案内記録は書き換えない。

### ③の帰結

- `98_願意・料金・時間枠等マスター` は、`祈願申込入力!98_マスタ` の **9区分・38願意をコピーして持つ**
  （別ファイルへの `IMPORTRANGE` は、参照先の権限切れで全画面が止まるため使わない）。
- 願意は正式名称。前札マスター(R2) の略称（事業／工事／繁栄／心願／交通／家内／健康／商売／海上／大漁／厄除／災難）は
  移行時に正式名称へ変換する。**略称にない自由記述**（`社員安全`／`関係者の健康`／`CD売上ヒット成就`）は
  `98` へ追加するか `その他`＋備考にするかを職員が判断する。
- 前札は既存区分の **`五万円祈願（前札）`** に対応する。新春一般は五千円〜三万円の区分を使う。

### ④の帰結

- `92` の過去年度行は、読上げ名簿から作れる **年度／氏名／読上げ順／申込あり** の4項目のみ。
  祈願日時・祈願料・入金は過去年度には入らない（R2 のみ前札マスターから補える）。
- R9 の案内状「昨年申込済み／新規」の出し分けは、**2025年の読上げ名簿**を前年実績として使う。

| # | 論点 | 決定 |
|---|---|---|
| ⑤ | 信者様の案内単位 | **個人単位**。`90` は1人1行。世帯IDは**一括領収書・同封の単位**としてのみ使う |
| ⑥ | 会社の本社・支店 | **分ける**。会社ID＋拠点IDを持つ |
| ⑦ | Google フォーム | **前札・新春一般の両方に作る** |
| ⑧ | 奉納品・授与品 | **`94_明細` に含め、数量と金額を管理する** |

### ⑤の帰結

- 井町家 6 名は `90` に 6 行、世帯ID `H-xxxx` を共有。`93` の申込も 6 件。
  領収書は「一括請求先申込ID」で 1 枚にまとめる。
- 小鶴家 3 名（雅子・照美・秀一）＋`合資会社小鶴石油` は、個人3行＋会社1拠点。
  世帯IDでまとめるかどうかは移行時に職員が判断する。
- 案内状の部数は「世帯ID単位で1通」にする集約オプションを、差込データ出力側に持たせる。

### ⑥の帰結

- `91` の主キーは **会社ID＋拠点ID**。`㈱ノリタケカンパニーリミテド` は会社ID 1つ、
  `久留米工場` が拠点 `-01`。`日本生命保険相互会社` も同様に `久留米支店`。
- 沖縄側の備考にあった「西原事務所×1.5万／コザ保守センタ×1.5万／名護支店×1.5万／宮古支店×1.5万　計6万」
  のような拠点別内訳は、**拠点ごとの申込 4 件＋一括請求先1件**として表せる。
- 本社単位の集計は会社IDで、拠点単位の案内は拠点IDで行う。

### ⑦の帰結

- `96_フォーム受信・処理エラー` を最初から作る。受信は**原文保存 → 台帳反映**の2段。
- フォームは**前札用・新春一般用の2本**。年度・受付状態は `99_設定` から反映する
  （年間法会の `syncFormScheduleInfo` と同じ方式で、設問の作り直しはしない）。
- 回答IDで既存行を検索してから追記。再処理しても二重登録・二重入金・二重メールにならない。
- フォームからの申込は **`93` の申込状態＝`受付中`** で入り、`確定` にするのは職員。
- トリガーの件数・種類・対象フォームIDを確認する診断メニューを用意する。

### ⑧の帰結

- `94_祈願・御札明細` の**御札種別**に「奉納品」を追加し、
  `お酒`／`御神酒`／`熊手`／`破魔矢`／`交通安全ステッカー`／`だるま`／`おもち代`／`その他` を持つ。
- 明細行は `種別・品名・数量・単価・金額`。祈願料と奉納品を合算した金額が申込の合計になる。
- R2 備考の『お酒5本』『御神酒4本』『特大矢×3』『熊手2尺×1』『交通(身代無)×7』は
  移行時に**職員が構造化する**（自動変換はしない）。単価が不明なものは金額 0 で品名と数量だけ残す。
- 授与品の在庫・単価は `98` に品名マスタとして持つ。

## 0-3. 決定事項（第3回）

| # | 論点 | 決定 |
|---|---|---|
| ⑨ | 前札の祈願形態 | **元朝の一斉読上げ＋希望者は個別枠も取る** |
| ⑩ | 祈願枠 | **30分刻み。1枠に複数組**（対象日・時間帯・上限は `99_設定`） |
| ⑪ | Google フォーム | **新規の方も受け付ける** |
| ⑫ | 領収書・請求書 | **要望があった場合のみ発行** |

### ⑨⑩の帰結 ─ `03_祈願予定` は2つの面を持つ

| 面 | 対象 | 1行が表すもの | 使う場面 |
|---|---|---|---|
| **読上げ一覧** | 元朝読上げの全件 | 読上げ順1件 | 大晦日深夜〜元旦。読上げ順・読上げ名・読み終わりチェック |
| **枠割付表** | 個別枠を希望した申込 | 枠×組 | 正月の日別確認。日・時刻・組・人数・願意 |

- `93_申込台帳` に **`元朝読上げ`（TRUE/FALSE）** と **`読上げ順`** を持たせる。
  個別枠を取る申込は、これに加えて祈願日・時刻を持つ。**両方を持つ申込がありうる**（読上げもし、参列もする）。
- 読上げ順は前年の順序を初期値として引き継ぐ。`元朝前札読み上げ.xlsx` 3世代とも
  ほぼ同じ並びだったため、毎年ゼロから並べ直す運用ではない。
- 枠は 30 分刻み・1枠複数組。**人数上限と組数上限の両方**を `99_設定` に持ち、
  超過時は登録を止めず「要確認」を付ける。
- **対象日・時間帯・上限値は未確定**。設定シートの初期値として仮置きし、第4回以降で確定する。

### ⑪の帰結 ─ 新規受付の工程が増える

- フォーム回答に対応する `92` の行がない場合、**`92` に「フォーム新規」の行を自動生成**する
  （案内ルート＝申込時に選択、案内状態＝`案内不要`、返答状態＝`申込済`）。
- 新規は `90`／`91` にも行がないため、**マスターへの登録は職員が行う**。
  それまで `93` は仮の対象IDを持ち、`要確認` に「マスター未登録」を付ける。
- 氏名・電話・住所の一致で**重複候補を検出して通知**する。登録は止めない。
- フォームは前札用・新春一般用の2本。**同じフォームで既存の方も新規も受ける**
  （案内IDの入力欄を任意にし、入っていれば `92` の既存行に紐付ける）。

### ⑫の帰結

- `93` の **`領収書要否`／`請求書要否` の既定値は `不要`**。申出があった行だけ `要` にする。
- 宛名は `91` の「領収書の宛名」「請求書の宛名」を使い、空欄なら会社名・氏名を使う。
- R2 備考の『領収書いらない』『〇誠様宛』『領収書一括』『ダルマ×1(領収書別)』は、
  それぞれ `要否＝不要`／`宛名`／`一括請求先申込ID`／**別申込に分ける**で表す。
- 礼状は別管理。`新春祈願礼状（現金）` の Google ドキュメントが既にあるため、
  `93` に `礼状要否` を持ち、差込データを出力する。

## 0-4. 決定事項（第4回）

| # | 論点 | 決定 |
|---|---|---|
| ⑬ | 案内状 | **11月に郵送。一括差込印刷** |
| ⑭ | 郵送料 | **寺院負担。祈願料に含む**（送料の列は持たない） |
| ⑮ | 翌年度の案内停止 | 辞退・死亡・転居不明・廃業・重複**のみ**で停止。加えて**一定年数の未申込で「要確認」**を付ける |
| ⑯ | トリガー所有アカウント | **年間法会受付管理と同じ管理用アカウント** |

### ⑬の帰結

- `92_年度別案内対象` の生成は **10月**、案内状の郵送は **11月**。年間スケジュールを §4 に合わせる。
- 一括差込印刷なので、`92` から**差込用データを1枚のシートへ出力**する機能を作る。
  出力列は 宛名・郵便番号・住所・建物名・敬称・案内状の種類（昨年申込済み／新規）・案内ルート。
- 案内状態は生成時に `案内予定`、差込出力で `印刷済`、投函記録で `郵送済` へ**一括更新**する。
  行ごとに動かす必要はない（順次発送ではないため）。
- 世帯IDが同じ信者様は**1通に集約**するオプションを差込出力に持たせる（第2回 ⑤の決定）。

### ⑭の帰結

- `94_祈願・御札明細` に送料の行を作らない。`98` にも送料の品名を持たない。
- 郵送で発生する実費は寺院の経費として扱い、この台帳では管理しない。
- ただし **同梱物は明細に残す**。`前札郵送御神酒お詫び.pdf` が残っているとおり、
  御神酒を同梱する運用があるため、奉納品として数量で管理する（第2回 ⑧の決定）。

### ⑮の帰結

- `90`／`91` の **翌年度案内状態** は、`継続` を既定値とし、
  `辞退`／`死亡`／`転居不明`／`廃業`／`重複` を選んだときだけ `92` の対象から外す。**理由は必須**。
- これとは別に、`92` の生成時に **直近 N 年連続で申込がない対象へ `要確認` を付ける**。
  対象から外すのではなく、職員が棚卸しする材料として出す。
- **N の値は未確定**。`99_設定` の「未申込要確認年数」として持ち、初期値は 3 年を仮置きする。
- 返戻は自動停止にしない。`92` の案内状態を `返戻` にし、住所確認のうえ職員が判断する。

### ⑯の帰結

- フォーム送信・onEdit・onChange のトリガーは、**年間法会受付管理と同じ管理用アカウント**で作成する。
- 「使い方」シートと診断結果の画面に、**そのアカウントで実行する必要がある**旨を明記する。
- 復旧関数 `repairShinsunFormTriggers`（仮称）は日常メニューに出さず、
  Apps Script エディタからの実行入口だけを残す。
- 診断は「フォーム送信トリガーが2本（前札用・新春一般用）、onEdit が1つ、onChange が1つ」を期待値とする。

## 2. 久留米の新春祈願の実態

調査の結果、久留米では **2 つのご案内ルート**が並行している。これは「信者様／会社」の切り分けとは一致しない。

| ルート | 案内状 | 申込用紙 | 対象 | 帳票 |
|---|---|---|---|---|
| **前札** | 前札案内（昨年申込済み）／（新規、昨年未申込）の**2種類** | 前札申込用紙 | 会社・法人・団体・個人が**混在** | 元朝前札読み上げ／札送り先／礼状・領収書 |
| **新春一般** | 新春一般祈願案内状 | 新春一般申込用紙 | 主に個人 | 一般祈願郵送者名簿 |

前札マスター(R2) の中身を見ると、`（株）熊丸組`（会社）と `冨安三十六`（個人）が同じ表に並び、
`久留米市長`『案内状は後援会長「植村浩二」様宛に送る』のように**宛名と祈願名義が別**の行もある。

さらに、単純な1社1申込では表せない実務が既に存在する。

- **連名**：井町家 6 名を1枚の領収書で受け、計 31 万円（うち自宅お祀り分 1 万円）
- **合算**：時里組から古賀誠・藤丸敏の分も併せて受け、計 15 万円
- **合同**：（株）101 と沖縄観光サービスが合同祈願で前札 1 本（沖縄側の例）
- **奉納品**：お酒 5〜20 本、御神酒 4 本、おもち代、特大矢×3 など祈願料と別枠
- **祈願なし**：「参列無し・前札のみ」「祈願無し、熊手のみ受取」「預け」

**案内状の文面が前年の申込有無で分岐している**点は特に重要で、
「前年に申込がなくても案内対象から外さない」という要件がすでに現場の運用として存在している。

## 3. 年間法会受付管理から採る／採らない

### 採る考え方

| 考え方 | 新春祈願での適用 |
|---|---|
| 日常操作シートと内部台帳を分ける | `0x_` 系（職員が見る）と `9x_` 系（自動更新）に分離 |
| 1申込1行 | `93_申込台帳` |
| 明細は1明細1行 | `94_祈願・御札明細`（御札1枚＝1行） |
| 入金は1入金1行 | `95_入金履歴`。合計・未収は台帳側へ集計 |
| IDで結ぶ | 氏名照合は補助。正の紐付けは全部 ID |
| LockService | 申込ID・入金IDの採番と登録処理 |
| フォーム回答の重複処理防止 | 回答IDで既存行を検索してから追記 |
| 取消・重複・テストを集計から除外 | `ANNUAL_V16.EXCLUDED_RECEPTION_STATES` と同じ考え方 |
| エラー時も受信内容を残す | `96_フォーム受信・処理エラー` |
| トリガーの診断と復旧 | `repairAnnualFormTriggers` 相当を管理者用に残す |
| 年度をコードに固定しない | 年度は `99_設定` から読む |
| 外部資料の一時的な読取失敗で確定情報を失わない | 過年度実績は**取り込み済みフラグ付きで保存**し、再取込で消さない |
| 職員が保守スクリプトを実行しなくてよい | 日常メニューは 3〜4 項目 |

### 持ち込まない機能

初盆／納骨壇前読経／供養内容／廻向証／経木塔婆／**1枠1組の予約規則**／
COVERAGE 行を履歴に混ぜる方式／氏名だけの履歴照合。

> 1枠1組は特に危険。沖縄の実績では 7:00 の枠に 6 社 57 名、16:30 の枠に 2 社 80 名が入っている。
> 新春祈願の枠は「1枠に複数組、上限は人数と社数の両方」で設計する。

```

11〜12月  ④ 申込受付（電話・窓口・郵送・FAX・Web）           → 02_受付入力 → 93_申込台帳
12月     ⑤ 祈願日時の割付・混雑確認                         → 03_祈願予定
12月     ⑥ 御札の浄書・準備                                 → 04_御札・準備一覧 ← 94_明細
```

`01` と `92` を分ける理由は、`01` が「絞り込んで見る画面」、`92` が「消してはいけない年度記録」だから。

枠×組で1行にし、日別ビューは集計で作る。

## 9. 状態の遷移

指定された状態を、実務で区別が必要なものに絞った案。

```
案内状態    未準備 → 案内予定 → 印刷済 → 郵送済／メール済／手渡し済
                                        └→ 返戻 →（住所確認）→ 再送 or 案内不要
返答状態    未回答 → 申込予定 → 申込済
                  └→ 辞退（理由を90/91のUへ反映）
                  └→ 連絡待ち → 要確認
申込状態    下書き → 受付中 → 日時調整中 → 確定 → 完了
                                          └→ 取消／重複／テスト（集計から除外）
入金状態    未入金 → 一部入金 → 入金済
                              └→ 過入金 → 要確認 → 返金
                    免除（志納辞退・寺院負担）
準備状態    未着手 → 作業中 → 浄書済 → 準備済 → 祈願済 → 受渡済／郵送済／預かり
翌年度案内  継続 ⇄ 一時停止
            └→ 辞退／死亡／転居不明／廃業／重複（＝案内対象外。理由必須）
```

**整理の提案が2点。**

1. 「実施状況（予定／実施済／中止）」を申込状態と分ける。申込は確定でも当日欠席がある。
2. 準備状態の「郵送済／受渡済／預かり」は**受渡方法（申込台帳P列）と組**で持つ。
   状態名だけで持つと「預かりのまま年度が終わった」件が見えなくなる。

## 10. 自動化する処理／職員が判断する処理

| 自動 | 職員が判断 |

| ID採番（LockService） | 同姓同名が同一人物かどうか |

| 前札祈願者マスター(R2) | 約170 | `90`／`91`＋`92`(R2)＋`93`(R2) | 半自動。個人／会社の判定は職員確認 |
| 元朝前札読み上げ 2023／2024／2025 | 各約175 | `92`（各年度） | 自動。名前と読上げ順のみ |
| R7新春一般祈願郵送者名簿 | 1（ほぼ空） | `90`＋`92`(R7) | 手作業 |
| 令和三年祈願者名簿 | 少数 | `90` | 手作業 |
| 沖縄 新春祈願管理（最新） | 企業98／申込136 | **移行しない** | 沖縄のデータ |

### 自動移行できる項目／できない項目

| 自動移行可 | 職員確認が必要 |
|---|---|
| 名称、フリガナ、電話番号、郵便番号、住所 | **個人か会社かの判定**（前札マスターは混在） |
| 願意の略称→正式名称の変換（事業→事業繁栄 等） | 略称にない自由記述願意（`社員安全`『関係者の健康』『CD売上ヒット成就』） |
| 年度別の申込有無（読上げ名簿の有無から） | 同姓同名・表記ゆれの名寄せ |
| 札送りの記号（〇／持参／来山／預／持帰） | 「〇(領収書一括)」のような複合値 |
| 祈願料 | 連名・合算の金額按分（井町家31万・時里組15万） |
| — | 奉納品の文章（『お酒5本』『特大矢×3』）の構造化 |
| — | 宛名注記（『案内状は後援会長「植村浩二」様宛に送る』） |

### 移行の原則

1. 元ファイルは**一切変更しない**。読み取り専用でコピーを作る。
2. 移行は `97_移行作業` シート（一時）に**元の行番号と元ファイル名を付けて**書き出す。
3. 職員が `97` で確認・分類してから `90/91/92/93` へ反映する。
4. 件数照合：移行元の行数、移行後の行数、除外した行数と理由を `99` のログに残す。
5. 過年度の `92` は**参照専用**とし、案内状態は「（過去実績）」で固定する。

## 12. 同時編集・重複・二重処理の安全対策

| リスク | 対策 |
|---|---|
| 同時登録でIDが重複 | `LockService.getScriptLock()` を採番と書込の両方を含む範囲で取得 |
| 空き行の奪い合い | 年間法会の `writeFirstEmptyIdRow_` と同じく、ID列の空欄を探して1行だけ確保 |
| フォーム回答の二重取込 | 先に `96` へ受信記録 → 回答IDで `93` を検索 → 既存なら追記しない |
| メール二重送信 | 「新規登録のときだけ送信」判定（`isNewSubmission` 相当） |
| 入金の二重計上 | `PAY-MAIN-<申込ID>` の固定IDで upsert。追加入金だけ新規ID |
| 同一人物の重複登録 | 電話・住所・世帯の一致で候補を出し、**登録は止めずに通知** |
| 同じ申込の重複受付 | 年度＋対象ID＋祈願札区分＋記載名 が一致したら要確認 |
| 訂正の取りこぼし | 訂正反映チェック＋訂正日時・訂正者・変更前後を残す |
| 途中エラーでのデータ消失 | 新しい内容を作ってから書き換え、余った旧行だけ消す |
| 過年度情報の消失 | 過年度の `92` は再生成の対象外。取込済フラグで保護 |

## 13. トリガーの確認・復旧

- `診断` メニュー：フォーム送信・onEdit・onChange の**件数・種類・対象フォームID**を一覧表示。
- インストール型トリガーは**作成者アカウントごと**に管理される旨を、診断結果の画面に明記する。
- 復旧関数は「**不足分をすべて作成できてから**、不要・重複・種類違いを削除」の順序。
  作成途中で権限エラーが出ても既存の正常なトリガーが残る。
- 復旧関数は日常メニューに出さず、Apps Script エディタからの実行入口だけ残す。
