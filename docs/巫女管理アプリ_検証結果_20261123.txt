----------------------------------------------------------------
0. この文書の使い方
----------------------------------------------------------------
- 指摘は優先度順（高 → 中 → 低）です。各項目に
  「場所（ファイル・関数）」「発生する操作」「期待結果と現状」「優先度」
  「修正方法」「修正後の確認方法」を書いています。
- 行番号は、検証用TXTの BEGIN FILE / END FILE で分割したファイル内の行番号です。
- 「要確認」は、実データ・運用設定・規程を見ないと結論が出ない項目です。
  推測で直さず、運用者に確認してください。
- 再現用のテストスクリプトをリポジトリの tools/miko-webapp-tests/ に置きました
  （付録A）。修正後は必ず全件を再実行してください。

1. 検証の方法と範囲
----------------------------------------------------------------
実施したこと:
  (1) 全 .gs と HTML 内のスクリプトの構文チェック → 両拠点ともエラーなし。
  (2) ファイルをまたぐ同名のトップレベル宣言 → なし。
  (3) google.script.run から呼べる関数（久留米18・沖縄20）の権限確認
      → すべて auth_() か requireMikoMaintenanceOwner_() を最初に通る
        （doGet と api の入口も確認済み）。
  (4) Code.gs と Payroll.gs を Node.js 上でそのまま読み込み、Apps Script の部分を
      仮の実装に置き換えて、依頼の重点項目を「実際に計算・保存させて」確認しました。
      配置の分割保存（writePlacementSplit_ / write_）は、メモリ上の仮シートで
      行位置まで確認しています。
  (5) 2拠点のファイル差分、付属画面（沖縄）の呼び出し元の照合。

実施していないこと:
  - 実際の Apps Script・スプレッドシート・フォームでの実行
    （保護・トリガー・フォーム受信は目視のみ）
  - index.html の全画面操作（E2E）
  - 源泉税額表（丙欄）の数値と国税庁の表との1行ずつの照合（下の M4）

3. 優先度【高】
----------------------------------------------------------------
[H1] 精算のたびに全配置の保護を張り直すので、シーズン末に処理時間を超える恐れ【要確認】
  場所: 両拠点 Setup.gs protectPaid_（久留米 62行）／ secureLedgerRange_（39行）
        呼び出し元: Payroll.gs の savePay_ / voidPay_ / receivePay_ / correctPay_、
        Code.gs の upgradeTravelColumns など
  発生する操作: 精算の確定・取消・受領・差額訂正のたび。
  現状:
    protectPaid_ は、精算済みのすべての配置1行ごとに secureLedgerRange_ を呼びます。
    secureLedgerRange_ は毎回 sh.getProtections()（シート上の全保護を取得）・
    getEditors()・removeEditors() などを実行します。
    精算済みの配置が N 行あると、1回の操作で N 回の保護取得が走り、N が増えるほど
    1回あたりの取得も重くなります。
  影響:
    シーズン末に全員を続けて精算すると（例: 50人×10勤務＝500行）、Apps Script の
    6分制限に近づき、保存の途中でタイムアウトする可能性があります。
    支払の行は書いた後なので、明細は残っても保護が途中までの状態になり得ます。
  修正方法:
    - 保護の一覧（getProtections）は1回だけ取り、説明（description）をキーにした
      Map を作ってから使い回します。
    - 今回の操作で状態が変わった配置（精算対象日に含まれる行、取消で外れる行）だけ
      を保護・解除し、全件の張り直しはやめます。全件の張り直しは管理者用の
      保守関数として別に用意します。
    - 行ごとの保護をやめ、精算済みの配置を「精算済み」列などで判定する方式も
      検討できます。ただし保護がなくなると直接編集を防げなくなるので、運用者と
      相談してください。
  確認方法:
    架空の台帳に配置500行・精算済み300行を作り、1人分の精算確定にかかる時間を
    実行ログで測ります（修正前と修正後を比べる）。

[H2] 権限の前提（USER_ACCESSING）による直接編集の扱い【要確認】
  場所: appsscript.json（両拠点とも executeAs: USER_ACCESSING / access: ANYONE）、
        Code.gs auth_（久留米 258行）
  現状:
    アプリへの入口は「管理者」か「人事担当の許可リスト＋台帳の編集者」に限られて
    おり、正しく守られています。ただしこの方式では、人事担当が台帳の編集権限を
    持つ必要があります。保護されていない表（人・勤務希望・必要人数・配置の未精算行
    など）は、アプリを通さずにシートを直接編集できます。
    その場合、重複・休憩・年齢・36協定などの点検と、同時編集の確認（base 比較）は
    すべて素通りになります。
  対応:
    - 運用ルールとして「シートの直接編集は管理者だけ」を明記します。
    - 必要なら人事担当には閲覧権限だけを付け、書き込みはアプリ経由にします。
      その場合、auth_ の「編集権限の確認」を「閲覧権限以上」に変える必要があります。
      ただし USER_ACCESSING のままでは、閲覧者は書き込めません。
      USER_DEPLOYING に変える場合は Session.getActiveUser() の取得条件
      （同一ドメインなど）の確認が必要なので、変更前に必ず運用者と相談してください。

4. 優先度【中】
----------------------------------------------------------------
[M1] 0:00交代の夜勤：両方を「出勤」で登録した後、後半を先に直すと保存できない
  場所: 両拠点 Code.gs actualOverlap_（久留米 858行）／ saveAttendance_（893行）
  発生する操作:
    「全員出勤」などで、前半 22:00〜0:00・後半 0:00〜6:00 を両方とも出勤登録する。
    その後、後半の実績開始を 23:55 に直してから、前半の終了を 23:55 に直そうとする。
  期待: どちらの順番で直しても、最終的に 23:55 交代で保存できる。
  現状:
    後半を先に直すと、まだ 0:00 までの前半と重なるので
    「同じ方の実績の時間が重複しています」で止まります。
    前半を先に直せば保存できます（テスト attend.js で確認）。
  修正方法（どちらか）:
    (a) エラー文で順番を案内する。重なる相手が同じ人・同じ勤務日・連続する配置
        （元の配置を分割したもの）なら、例えば「先に前半（〜0:00）の実績終了を
        23:55に直してください」と表示する。
    (b) 前半・後半を1回の操作で保存できる「交代時刻をまとめて直す」機能を作る。
        2行を一緒に検証・保存する。
  確認方法: tests/attend.js の「両方出勤済み・後半→前半」が OK になる（(b)の場合）。
    (a)の場合は、案内文が出ることを確認します。

[M2] 差額明細から再訂正しようとしたときのエラー文がわかりにくい
  場所: 両拠点 Payroll.gs correctPay_（久留米 248行）
  発生する操作: 未受領の差額明細（原支払IDあり）を対象に、さらに差額訂正を呼ぶ。
  期待: 「差額の再訂正は元の精算明細から登録してください」と案内される。
  現状:
    先頭の確認で「支払済みでない」と判定され、「支払済みの行と訂正理由を確認して
    ください」という別の文になります。案内文が出るのは、差額明細が受領済みの
    場合だけです。
  修正方法: 先頭で old.原支払ID を先に判定し、元明細へ誘導する文を返します。
  確認方法: tests/correct.js の「差額明細からの再訂正」が、元明細へ誘導する文で
    止まることを確認します。

[M3] 確定を取り消した差額と同じ受付番号で再送すると、何も作られずに成功扱いになる（低頻度）
  場所: 両拠点 Payroll.gs correctPay_ の previous の探し方
        （requestKey があると、取消済みの行も「既に登録済み」として扱う）
  発生する操作:
    差額を登録 → その差額を確定取消 → 画面に残った同じ受付番号で、同じ内容を再送。
  現状: エラーにならず「保存しました」と表示されますが、新しい明細は作られません。
  修正方法:
    previous が確定取消済みのときは、
    「この受付番号の差額は取り消されています。新しく登録し直してください」と
    エラーにします。画面側（index.html の correctionSave）は、取消後には
    受付番号を作り直します。
  確認方法: tests/correct.js の「取消後、同じ受付番号で再登録」がエラーになる。

[M4] 源泉税額表（丙欄）の数値を国税庁の表と照合する【要確認】
  場所: 両拠点 Setup.gs taxSeed_（2026年148行・2027年146行。両拠点とも同じ内容）
  内容:
    2026年は「9,800円から1円」、2027年は「10,000円から1円」で始まり、2027年は
    改正後の表を反映したものに見えます。ただし数値そのものの正しさはコードからは
    判断できません。
    支払予定日の年（payDate の年）で表を選ぶので、1月支給は2027年の表になります。
  確認方法: 国税庁の「給与所得の源泉徴収税額表（日額表）」の丙欄と、全行を
    突き合わせます（境界・税額・超過分の率）。特に 32,500円・57,500円（2027年は
    58,000円）・116,500円の行の計算式を確認してください。

[M5] 1週間の区切りと、シーズン途中の精算【要確認】
  場所: 両拠点 Payroll.gs monday_ / classify_、calculate_
  内容:
    - 週40時間の判定は「月曜始まり」です。就業規則に週の起算日の定めがなければ、
      法令上は日曜始まりとして扱うのが一般的です。規程を確認し、必要なら設定項目に
      してください。
    - 未精算の配置に「予定」が1件でもあると精算できません
      （「未確認の勤怠があります」）。途中で辞める人を先に精算する場合は、
      先に残りの予定を取り消す運用になります。この運用でよいか確認してください。
    - 端数調整は差引支給を100円単位に「切り上げる」（最大99円を加算する）方式です。
      会社負担で多く払う方向なので法令上は問題ありませんが、規程と合っているか
      確認してください。

[M6] 2拠点のコードがコピーから分かれ、同じ機能の実装がずれている
  差分の行数: Code.gs 131 / Setup.gs 391 / index.html 178 / Payroll.gs（久留米だけ
  能力給・日別時給内訳あり）/ MaintenanceSecurity.gs（トリガー確認の方式が違う）
  主な違い（意図的かどうかを運用者に確認）:
    - 能力給（50/100/150円）と日別時給内訳: 久留米のみ。
    - 手入力交通費の上限: 久留米は500円で止める（manualMax:500）。
      沖縄は上限なしで、基準の最高額を超えると確認を求める（manualMax:null）。
    - 勤務帯の「休憩予定分」（時刻未設定の休憩を配置前に止める）: 沖縄のみ。
    - 台帳の世代管理: 久留米は '台帳世代'、沖縄は '職員画面の台帳世代'
      （沖縄は値がなければ自動で作る）。
    - 年度切替: 久留米は switchLedger / restorePreviousLedger があり、フォームの受付
      期間も記録する（receptionHistory_）。沖縄には切替の関数がありません。
    - フォーム受信: 久留米は期間で回答を絞り込み、送信1件ずつ処理する。
      沖縄は毎回フォームの「全回答」を取り込む（pullResponses_、沖縄 Setup.gs 208行）。
      → 沖縄で次年度も同じフォームを使うと、前年度の回答まで新台帳に入ります。
        また、回答数が増えるほど1回の受信が遅くなります。【要確認】
    - 応募トリガーの確認（requireMikoTriggerContext_）: 久留米は終了したトリガーや
      送信元フォームまで照合する。沖縄は登録済みトリガーの照合だけ。
  修正方法:
    1つのソースにまとめ、拠点の違いは設定で切り替えます（例:
    SITE_FEATURES = {KRM:{merit:true, manualFareMax:500, ledgerSwitch:true},
    OKI:{breakMinutes:true, manualFareMax:null}}）。
    少なくとも沖縄のフォーム受信と年度切替は、久留米の実装を移植するか、
    「次年度は必ず新しいフォームを作る」運用を手順書に書いてください。

[M7] 沖縄 mikoHrEmails_ に人事担当アドレスの既定値が直接書かれている
  場所: 沖縄 コード.gs 277行
    const text = configured == null ? 'hr-review@example.invalid' : String(configured);
    （外部レビュー用にダミー値へ置き換え済み。原本では実在のアドレス）
  影響:
    スクリプトプロパティ MIKO_HR_EMAILS を消すと、コードに書かれた人に権限が戻ります。
    担当者が替わったときに、権限を外し忘れる原因になります。
  修正方法:
    既定値をやめ、プロパティが未設定なら空（＝管理者だけ）にします。
    現在の担当者は MIKO_HR_EMAILS に明示的に登録します（久留米と同じ方式）。

[L1] 沖縄の付属画面4ファイルは現在使われていない
  場所: 沖縄 AnnualPage.html / Field.html / MailTemplatesPage.html / ShiftBoard.html
  照合結果:

    → 現行の職員画面への影響はありません。中に個人情報らしき値は見つかりません
      でした（ダミーのメールアドレス1件のみ）。
  修正方法: 合計約90万文字あるので、Git などに保管したうえでプロジェクトから削除します。

[L2] 同じ勤務日の中抜け（2時間以上）で「休息が短い」という注意が出る
  場所: 両拠点 Code.gs issues_（継続判定 continuesDuty_ が間隔120分以上を
        別勤務と扱うため）
  例: 午前9-12時と午後15-19時（同じ日）→「前の勤務からの休息が短くなっています」。
  影響: 交通費・時間外の計算は正しい（1回・同じ勤務日）。注意の表示だけが不正確です。
  修正方法: 同じ配置日（a.日付が同じ）の間隔は休息の注意から外し、中抜けとして
    扱います。コードのコメントもその意図になっています。

[L3] 年度切替の後の税額表・最低賃金
  nextYear_ は現在の設定（税額表・最低賃金を含む）を新台帳にコピーします。
  次の年の「丙欄:翌年」「最低賃金:改定日」がない場合、精算時に
  「税額表が未登録です」で止まります（安全側の挙動）。年度準備の手順書に
  「税額表と最低賃金を追加する」を入れてください。

6. 問題がなかった項目（参考）
----------------------------------------------------------------
- 権限: api は ScriptLock を取ったうえで auth_ を通り、精算・設定・移行などは
  auth_(s,true)（管理者のみ）。保守関数は requireMikoMaintenanceOwner_、
  トリガーは requireMikoTriggerContext_ で、登録済みトリガーかを照合しています。
- 同時編集: put_ / unchanged_ による base 比較、ledgerSession による
  「表示中の台帳が切り替わった」の検出。
- 配置の分割: 休憩の途中での分割禁止、移動先の定員・大学生以上の枠の確認、
  1回の batchUpdate での保存、追加先の行が空であることの確認。
- 台帳の保護: 支払・設定・メール文面・列名・実休憩分の式・精算済みの配置行は、
  管理者だけが編集できます（警告のみではない保護）。
- 画面のエスケープ: E() が & < > " ' を変換しており、利用者の入力（氏名・メモ等）は
