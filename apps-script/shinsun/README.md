## 導入手順

### 1. コードを貼る

1. 上記スプレッドシートを **rusuiramuka@gmail.com** で開く。
2. 「拡張機能 > Apps Script」を開く。

### 自動で起きること

- **ID採番**：氏名・会社名を入れた行に ID が付く。`LockService` で採番と書込みを保護しているので、
  2人が同時に入力しても ID は重複しない。
- **既定値**：敬称・案内方法・翌年度案内状態が空欄なら埋まる（個人は `様`／会社は `御中`、いずれも `郵送`・`継続`）。
- **同姓同名の通知**：同じ氏名が既にあると通知が出る。**登録は止めない。**
  別人ならそのまま登録し、同一人物なら既存行を更新する。
- **停止理由の督促**：翌年度案内状態を `継続` 以外にすると、案内停止理由の欄が赤くなり通知が出る。
  理由のない案内停止は行わない。

## 設計上の決まり（段階2以降も守る）

- **固定列番号を使わない。** 列は `headerMap_()` で見出し名から解決する。
- **年度・料金・時間枠・フォームID・アカウントをコードに書かない。** すべて `99_設定` から読む。
- **ID採番は書込みまで含めてロックの中で行う。**
- **読み書きは一括。** 1行ずつのループで台帳を読み直さない。
- **`onOpen` はメニュー表示だけ。** シート構成の修復・全件再集計はしない。
- **`onEdit` で全件再集計しない。** 編集された行に関係する範囲だけを更新する。
- **新しい内容を作ってから書き換え、余った旧行だけ消す。**
- **自動メールは `99_設定` の「自動メール有効」が FALSE の間は送らない。** 段階9の承認まで FALSE のまま。

| 列 | 誰が入れる |
|---|---|
| `移行ID`〜`生データ` | 取り込みが入れる。元の行が丸ごと `生データ` に残る |

## 3. 取り込みの仕方（元資料の形に合わせている）

- **元朝前札読み上げ**：シート名を年度、1セル1名として読む。
  読上げ順は `99_設定` の「読上げ順の方向」に従って仮に付ける。
  **既定は行方向**（左から右、次の行へ）。実資料を確認したところ、
  同じ家・同じ会社の名前が一つの行に連続して並んでいたため。
  印刷の並びと違えば設定を「列方向」に変えて取り込み直す。
  なお段階2を先に実行済みの場合、`99_設定` の既存の値は上書きされないので、
  セルの値を手で「行方向」に直してから取り込み直すこと。
- **前札祈願者マスター(R2)**：この資料は形がそろっていないため、次のように読む。
  - 見出し行が資料の途中で何度も現れる（①②…と章が変わる）。
    見出しは**上書きせず積み上げる**。後の章の見出しには
    「前札名称・願意その他・札送・来山予定」しか書かれていないが、
    電話番号や備考の列は最初の見出しと同じ位置にあるため、前の章の位置を引き継ぐ。
  - 章によって「前札名称」の列がずれる（①はE列、②以降はG列）。
    積み上げた見出しで上書きされるので、そのまま追従する。
  - 見出しは結合セルなので、値は結合の左上にしか入らない。
    各見出しは**自分の列から次の見出しの列の手前まで**を受け持つ範囲とみなし、
    その範囲の中身をすべて拾う（「願意」は17・19・23列目に散っている）。
  - 前札名称の欄には「前札の名義」と「内札の名義」が並ぶ。
    内札が始まる列を資料全体から数えて決め、前札名と内札名を分ける。
  - 内札だけの行は**捨てずに別の行として出す**。一つの前札に内札が何名も付くため。
    `要確認` に「内札欄だけの行。前札「○○」の内札として記載。」と残す。
  - 「お酒10本」「自宅お祀り分1万円」のように数字と単位を含む覚え書きは
    名前ではなく直前の記録の奉納品として結合する。
  - 願意・奉納品だけの行は直前の記録の続きとして結合し、
    `要確認` に「続き行を結合（n行）」と残す。
  - 「令和2年　新春特別祈願者」だけの行は章の見出しなので名前として扱わない。
- **一般の名簿**：氏名・〒・住所などの見出しを見つけて読む。
  **名前が空でも、住所・電話・金額・願意のどれかがあれば取り込む**。
  `要確認` に「名前欄が空です。元資料で氏名を確認してください」と残す。
  実資料（R7新春一般祈願郵送者名簿）に名前だけ空の申込が1件あったため。

# 段階3｜分類と 90／91／92 への反映

コードは `03_移行反映.gs`。仕様書 §10 では `07_移行.gs` に書き出しと反映をまとめているが、
1ファイルが長くなりすぎるため反映だけを分けた。Apps Script はファイルを分けても互いに呼べる。

## 1. 手順

1. Apps Script エディタで `setupShinsunStage3` を実行
   - `92_年度別案内対象` を作る
   - `98_マスター` の案内状態へ「（過去実績）」を足す
   - `97_移行作業` の「処理」に「履歴のみ」を足す
2. `suggestShinsunClassification` を実行（分類の下書き）
3. **`97_移行作業` を職員が確認して直す**
4. `applyShinsunMigration` を実行（`90`／`91`／`92` へ反映）
5. `checkShinsunMigration` で残りを確認

## 2. 分類の下書きの決め方

実資料（前札祈願者マスターR2）を見て決めた順序。すべて下書きで、職員が上書きできる。

| 順 | 条件 | 区分 | 確定名称 |
|---|---|---|---|
| 1 | 名称に法人格・業種の語がある（`(株)` `組合` `幼稚園` `建設` `店` など）| 会社 | 名称（生） |
| 2 | 名称が肩書き・自治体名（`久留米市長` `衆議院議員` `北九州市`）で内札名がある | 信者様 | **内札名** |
| 3 | 同上で内札名がない | 空欄 | 名称（生） |
| 4 | 法人格の語はないが、内札欄に別の名前がある（`テクノ／中園孝一`）| 会社 | 名称（生） |
| 5 | どれにも当たらない | 信者様 | 名称（生） |

1 を 2 より先に見るのは、`(株)シミズ・ビルライフケア 九州支社 災害防止協議会` のように
法人格と肩書きの語を両方含む名前があるため。

実データでの結果：637件を 信者様455／会社180／空欄2。
迷いのある行（要確認に理由を書いた行）は40件で、内訳は
肩書き・自治体名17件、内札欄に別の名前があるため団体とした21件、名称が空2件。

読上げ名簿186名を試したところ、会社と判定した28件はすべて実際に会社で、
個人を会社と見た例はなかった。

既知の弱点。

- `寺` を法人格の語に入れているため、`寺田` `寺本` のような姓を会社と判定する。
  今回の資料には該当がないが、新しい資料を入れるときは要確認。
- `写真の光陽` `シビルウェブ` のように法人格の語も内札名もない屋号は個人と判定する。
- `小林康子／川瀬露秋` `大賀 誠治／大賀歯科医院` のように、
  内札欄に別の名前がある個人を団体と判定する。要確認が付くので職員が直せる。

処理は、読上げ名簿は `履歴のみ`、それ以外は区分が決まった行だけ `登録する` を入れる。

## 3. 「処理」の意味

| 処理 | 90／91 | 92 |
|---|---|---|
| 登録する | 新しい行を作る | その年度の過年度行を作る |
| 既存に統合 | 対象IDの既存行へまとめる（印だけ付ける）| 過年度行を作る |
| 履歴のみ | 増やさない | 過年度行だけ作る（読上げ名簿）|
| 対象外 | 何もしない | 何もしない |
| 未分類 | 何もしない | 何もしない |

## 4. 反映のきまり

- 反映した行は `97` の **反映状態＝反映済**・**対象ID**・**反映日時** を書き戻す。
  すでに反映済の行は読み飛ばすので、**何度実行しても二重には入らない**。
- 読上げ名簿の対象IDは、`90`／`91` に**同じ名称が1件だけ**あるときだけ結ぶ。
  0件・2件以上のときは対象IDを空欄にして要確認に理由を書く。**推測で結ばない。**
- `92` の過年度行は案内状態 **「（過去実績）」** で固定。案内対象の再生成では作り直さない。
- 年度は 令和＝西暦−2018 で換算する（2025→R7、2024→R6）。
  読上げ名簿の **「編集中」シートは年度が決められない**ため `92` へは入れず、要確認に残す。
  `97` の年度欄へ `R8` のように入れて実行し直せば反映される。
- 内札欄だけの行（井町千春など）は `90` へ個人として登録し、職員メモに親の前札名を残す。
  段階6で `94_祈願・御札明細` として結び直す。
- 会社の内札名義は `91` の **内札の記載名** に入れ、職員メモに
  「代表者名の可能性あり」と残す。元資料の欄名どおりにして、勝手に代表者名としない。

## 5. 92_年度別案内対象 の列

仕様書 §4 の24列に加えて2列を持つ。

| 列 | 理由 |
|---|---|
| `読上げ順` | 仕様書 §13「過年度に入る項目」で必要。`93_申込台帳` は段階6のため、ここに置く |

# 御札の記載名について（段階3で 90 に列を足した理由）

久留米の実際の運用。

- **前札（五万円）は外札と内札の2枚**を作る。**新春一般には外札がなく、一般札だけ。**
- **外札**：個人でも会社（議員）でも、個人名で上げてほしい方には
  **自治体名と個人名**で作る（「飯塚市　小鶴照美」「北九州市　吉田眞由美」）。
- **内札**：個人名の申込なら個人名だけ。会社なら会社名だけのことも、社長名のこともある。
- 内札・外札は申込者の希望どおりに作る。

つまり **案内状の宛名と、札に書く祈願者名は一致しない。**

仕様書 §4 では `91_会社マスター` にだけ「外札の記載名」「内札の記載名」を置いていたが、
個人にも外札・内札の別があるため `90_信者様マスター` にも同じ2列を足した。

移行での対応。

| 元資料の欄 | 意味 | 移行先 |
|---|---|---|
| 前札名称 | 外札に書く名前 | `外札の記載名` |
| 内札名称（代表者名（生））| 内札に書く名前 | `内札の記載名` |
| 確定名称（職員が決める）| この方は誰か | `氏名` ／ `会社・法人・団体名` |
| — | 案内状の宛名 | `案内宛名`。肩書きなら「肩書き　個人名」、自治体名なら個人名だけ |

内札欄だけに書かれていた行（井町千春さまなど12件）は、外札ではなく内札の名前なので
`外札の記載名` は空、`内札の記載名` にその名前を入れる。

## 3. 楽まる寺務の読み方

クエリ `Q101_申込一覧_エクセル`。**1行 ＝ 祈願者1名**で、同じ整理番号の行が
まとまって申込1件になる。

- **申込者（整理番号）** … 案内状・請求・領収書の相手 → `90`／`91`
- **祈願者（申込番号）** … 札に書く名前 → 段階6で `94_祈願・御札明細`

`97_移行作業` には2種類の行を出す。

## 4. 名寄せ

同じ方が祈願料ごとの別ファイルに載っている。整理番号はファイルをまたぐと別番号なので、
**名称で照合する**。`登録する` の行で名称が1件だけ一致する既存行があれば、
新しい行を作らずそこへ結び、要確認に
「同じ名称の既存行（P-0007）に結びつけました。別の方であれば分けてください」と残す。

見込み：340申込者 → **90/91 に279行**（61件が既存へ結びつく）。
下書きの判定は 会社217／信者様118／空欄5、迷いのある行16。

## 5. 落とさないための処理

- 祈願者の会社名・役職・氏名がどれも空の行が **43行** ある。札は出ているはずなので
  捨てず、申込者の名前を入れて要確認を付ける。
- 申込者の会社名・施主名・家名がどれも空の行が **5行** ある。同じく残して要確認。
- 整理番号は A列で添字が 0 になる。**0 は偽値**なので `undefined` かどうかで見る
  （`!map.serial` と書くと1件も読めない）。

## 6. 楽まる寺務の申込者は、札の名前を持っていない

`90`／`91` の `外札の記載名`／`内札の記載名` は、楽まる寺務から入れた行では**空欄**にする。
札の名前は祈願者の行にあり、段階6で `94` から決める。
ここに会社名を入れると、実際の札と違う名前が台帳の既定になってしまう。

## 7. 暑中見舞の名簿

楽まる寺務の同じクエリで出ているため列は同じだが、祈願の申込ではなく**宛先名簿**。
祈願者の欄はほぼ空で、敬称（様／御中）だけが全行に入っている。
移行元の `ownerOnly` を立てて、祈願者の行は作らない。

| 移行元 | 行 | 宛先 | 備考 |
|---|---|---|---|
| 令和8年暑中見舞（僧侶）| 約78 | 同数 | 家名の欄に「僧」 |
| 令和8年暑中見舞（一般）| 264 | 264 | **〒・住所・敬称が100%** |

`行事` に `暑中見舞`、`案内ルート` に `暑中見舞（僧侶）`／`暑中見舞（一般）` を足した。
祈願ではないので `93`／`94` は作らず、`90`／`91` と `92`（案内の記録）だけ。

## 8. 敬称は元資料の値を使う

`祈願者敬称` の列を `敬称（生）` として取り込み、`90`／`91` の敬称に入れる。
空欄のときだけ 個人＝様／会社＝御中 を既定にする。
暑中見舞の名簿では全行に入っているため、そのまま使える。

## 9. 移行元のIDは 99_設定 に入れてある

`00_定数.gs` の `CONFIG_SEED` に変換済みスプレッドシートのIDを書いてある。
設計上の決まり「外部ファイルIDをコードへ埋め込まない」に対しては、
これは**初期値**であって、動くときは必ず `99_設定` から読む。
IDを変えるときは `99_設定` のセルを直せばよく、コードは触らなくてよい。

## 10. 古い資料の処理をそろえる

`relabelLegacyShinsunActions` を実行すると、楽まる寺務より前の資料の処理を
`登録する` から `履歴のみ` へまとめて変える。下書きは空欄の行しか埋めないため、
すでに `登録する` が入っている行はこれで直す。処理の列だけを変え、
区分・確定名称・対象IDには触らない。反映済の行も触らない。

## 12. 名簿区分（一般／僧侶）

`90_信者様マスター` に `名簿区分` の列を足した。暑中見舞（僧侶）の名簿から入った方は
自動で `僧侶` になる。案内状の文面と宛名を分けるために使う。

僧侶の名簿は**会社名の欄が寺院名**（成田山豊栄寺など）で、宛先は施主名（僧侶の氏名）。
そのままでは下書きが「会社」と判定して `91` へ入れてしまうため、この移行元だけ
`personFirst` と `kubun: '信者様'` を立て、施主名を名称にし、
寺院名は職員メモへ回して「案内宛名に入れるか確認してください」と要確認を付ける。

## 13. 前札の申込者と暑中見舞の宛先の食い違い

名前の文字合わせなので、表記違いを漏れと見てしまうことがある。職員が確認できる形で出す。

# 全角カッコの落とし穴（2回やった）

`clean_` は `String.normalize('NFKC')` を通すので、**全角カッコ「（）」が半角「()」になる**。
シートから読んだ値を、コードに書いたままの全角の文字列と比べると一致しない。

これまでに2回起きた。

| いつ | 何が起きたか |
|---|---|
| 段階1 | `99_設定` の `西暦（現在年度）` `枠の刻み（分）` が「ありません」と出た |
| 段階3 | `97_移行作業` の処理 `明細（段階6）` が集計で未分類に数えられた |

**決まり：clean_ を通した値と比べる文字列は、比べる側も clean_ を通す。**

```javascript
const detailAction = clean_('明細（段階6）');
if (action === detailAction) { ... }
```

`col_` `configValue_` `hasConfig_` は中で clean_ を通しているので、そのまま呼んでよい。
気をつけるのは、自分で `===` や `indexOf` で比べるときだけ。

今後この形の値を増やすときは、**カッコを使わない名前にするのが安全**
（`明細・段階6` のように）。`92` の案内状態 `（過去実績）` は書くだけで比べていないため
いまは問題ないが、段階4で比較するときは clean_ を通すこと。
